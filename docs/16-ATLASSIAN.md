# Atlassian integration: Jira, Bitbucket, Confluence (Cloud)

Status: design, 2026-10-23 (request R-023). Priority 2 after GitHub (priority 1). Built for a specific customer who runs the full Atlassian Cloud stack instead of GitHub. Everything marked **[SPIKE]** is unverified; do spike J1–J6 first (`docs/08`) and record results.

## What sits where
| Tool | Job | In Product Velocity |
|---|---|---|
| Jira Cloud | Work tracking: epics, stories, tasks, sprints, status | The delivery tracker for a project (replaces GitHub Issues) |
| Bitbucket Cloud | Code, branches, pull requests, pipelines | Delivery evidence (PR and pipeline state), linked through Jira issue keys |
| Confluence Cloud | Written pages | Optional links from an initiative to pages; no data lives there |
| Product Velocity | What to do, in what order, why, who agrees, what happened | Owns rank, value, confidence, customers, decisions, alignment, outcomes |

## Principles
1. **A project links to exactly one delivery tracker (built in 0.16.0: `projects.tracker`, guards PV008)**: GitHub, (later GitLab) or Jira. Jira is a peer of GitHub, not an add-on. The GitHub sync is put behind a provider interface first so both share the same rules (#67).
2. **Same boundaries as GitHub.** Commercial fields never go to Atlassian (rule 2; allowlist test on every outbound payload). Jira-driven fields (status, sprint, delivery progress, PR and pipeline state) are read-only in the app (rule 6). Writes are made by the app with an "on behalf of" line, need explicit user confirmation, and are audited (rules 3, 5). Text from Jira, Confluence and Bitbucket is data, never instructions (rule 4).
3. **Customer-specific mapping.** Jira sites differ in issue types, hierarchy, workflows and custom fields. Every connection has a mapping step; nothing is assumed.
4. **Nothing is written to Jira until the user has seen the exact changes and confirmed.**

## The two steps (Ashu, 2026-10-23; step 2 superseded by the update above)
### Step 1. Read and understand (read-only)
- Connect a Jira Cloud site (Atlassian OAuth 2.0 app, read scopes only) and pick the Jira projects to read. **[SPIKE J1]**
- Read open issues (not Done), issue types and hierarchy levels, statuses and status categories, sprints, versions, components, labels, assignees, dates, links, and custom fields. **[SPIKE J2]**
- Produce a **Jira map** report: how the open work is sliced. Counts by Jira project, type, status category, epic, sprint, age, last update; issues with no epic; epics with no open children; stale items; likely duplicates (similar titles); size of backlog per team or component. Claude may propose groupings as drafts; a human accepts.
- Import into a **staging area** in Product Velocity (not into the live roadmap): each Jira issue appears as a staged record with its Jira key and link. The user chooses the **level mapping** (which Jira level becomes Initiative, Epic, Task; default proposal: Jira Epic → Initiative, Story/Task → Epic or Task by size, Sub-task → Task) and the **field mapping**; the app shows a preview and what is skipped, and why.
- Accepting creates Product Velocity items linked to their Jira issues. Re-reading is repeatable and idempotent.

### Step 2. Clean up in Product Velocity, then sync back and maintain (two-way)
- **Clean up** in the normal grid, with undo: merge duplicates, split large items, regroup under Initiative Groups, close or drop what is dead, rank the rest. Changes to linked items collect in a **pending change-set**.
- **Review and push:** "What will change in Jira" shows every create, update, link and transition per issue; the user confirms (all, or selected). Pushes are idempotent and audited; undo creates the reverse change (a Jira transition cannot always be undone silently, so the preview says so).
- **Maintain, two-way:** Product Velocity → Jira for the allowlisted fields (name, description, labels, parent links, dates, priority, MoSCoW as a label or custom field per mapping); Jira → Product Velocity for status, sprint, assignee, progress, dates, PR and pipeline state. Webhooks (or polling if webhooks are unsuitable) are idempotent. Conflicts are highlighted and logged as for GitHub (`docs/04`). Status changes in Jira always win for Jira-driven fields; transitions follow the customer's workflow rules, so the app only requests transitions that the workflow allows. **[SPIKE J3, J4]**
- Confirmed by Ashu 2026-10-23: step 2 is clean up in Product Velocity, then write back and maintain two-way.

## Choosing what comes in: pull in, leave out, ignore (R-024, applies to GitHub too)
_Built for GitHub in release 0.15.0 (#76): tables `tracker_issues` and `tracker_rules`, page `/incoming`. Jira reuses the same model with `provider = jira` when #69 and #72 are built; levels (Initiative, Epic, Task) and parents arrive with the field mapping (#70). On GitHub a pulled-in issue becomes an Initiative that follows the issue read-only._
Not everything in the tracker belongs in the roadmap (bug tickets, chores, support requests). Nothing is pulled into Product Velocity just because it exists.
- **Three states for every tracker issue the app knows about:** **Not pulled** (default for anything new), **Pulled in** (becomes or links to an item in the roadmap), **Ignored** (deliberately left out, with an optional reason). Not pulled and Ignored are both reversible at any time: "not" never means "never".
- **Kept out of Product Velocity work:** not-pulled and ignored issues are not items. They do not appear in the grid, the Stack Rank, planning cycles, capacity or fit line, alignment, gates or reports. Product Velocity never writes to them (no updates, no transitions, no comments).
- **Light record, so they can come back:** the app stores only key, title, type, status, link and parent (tenant data, RLS) so the **Incoming** list can show them and a later pull is one click. They are re-read on sync to keep status current but nothing else is derived.
- **Pull-in keeps the issue's text and labels, and Re-pull (issue #365, parity with GitHub #364, 2026-11-09).** When a person pulls a Jira issue in, the issue is read once with the connection and the new initiative gets what is empty: **Description** (the Jira description converted from Atlassian document format to Markdown by `adfToMarkdown`: paragraphs, headings, bold, italic, code, http(s) links, lists, code blocks, quotes, plain tables; media left out; cut at 20,000 characters; our markers and @mentions neutralised; a description Product Velocity wrote uses its Description section, else its Summary), **Change Type** from exactly one `type:` label (feature, improvement or enhancement, bug) and **Focus Area** from exactly one `area:` label (`labelFields`, the same rules as GitHub; labels as Jira shows them now, else the Incoming record's). Done by `jira_copy_issue_description()` and `jira_copy_issue_labels()` (service role; creator or admin who is a person; only an initiative with source "Jira issue KEY" and a Jira link of either mode; only while the field is empty; audited as the person). The **Jira issue type (Bug, Story, Task, Epic) is never mapped to Change Type** (Ashu, 2026-11-09). On the **Pulled in** tab the same **Re-pull** button as GitHub fills what is still empty again; nothing is ever replaced and nothing is written to Jira. A failed read leaves the field empty with a note and never undoes the pull-in; a refused sign-in says to sign in again.
- **Incoming list:** a triage screen per connected project: filter by type, label, component, Jira project, age; select many; **Pull in** (choose level: Initiative, Epic or Task, and parent) or **Ignore** (with reason). Un-ignore and pull in later from the same list ("Ignored" filter).
- **Rules for new arrivals:** simple saved rules per connection, for example "issue type Bug → Ignore", "label support → Ignore", "Jira project OPS → Ignore". Rules only decide the default state of new arrivals; they never change an item already pulled in, and a person can always override.
- **Step 1 (read-only discovery):** the Jira map counts everything it read, including what will be ignored, because the slicing is the point. Accepting staged items is the same decision: pulled in or not.
- **Epic keys at creation (built 2026-11-15, issue #431, slice 4).** A person who already knows which Jira epics belong under an initiative lists their keys (typed, pasted, or as links; any Jira project) in the **Epics under this initiative** section of the initiative's Jira tab (for an initiative with no Jira issue yet, or one Product Velocity owns; not for a read-only one). That only records the request (`item_jira_epic_requests`: pending, linked or failed; one epic can be wanted by one initiative at a time; an initiative's own Jira issue cannot be requested); **nothing is written to Jira**. **Relaxed 2026-11-18 (issue #528, Ashu: listing the ID is the approval):** when **Sync with Jira** runs for an initiative that already has its Jira issue and is owned by Product Velocity, the epics listed on it that have **no parent** (and those already under it) are linked at once, with no confirmation; the card says what was linked. An epic that is **under another parent** (a move) is still shown in the preview and confirmed; an initiative whose issue does not exist yet keeps the confirmed send (it creates the issue first). Claude can list epic keys with `request_jira_epics` (records only). The text below describes the preview and confirmed send that remain for moves and for creating the issue. **Sync with Jira** shows each epic in the initiative's card under "Epics under this issue" (it reads the epics and the project's initiative type: an epic that does not exist or is not visible, is not at Epic level, or a project whose initiative type is not above Epic, is shown with the reason and not written; one already under the Initiative is shown as such; one under another parent says "moves under it (now under X)"). After the person **confirms**, the send creates the Jira Initiative first if it does not exist (as before), then sets each epic's **parent** to it (`PUT /issue/EPIC {fields:{parent}}`, the only thing written to an epic, proven across projects including team-managed R8P, `docs/08`), one call each; an epic Jira refuses is recorded as failed with Jira's reason and does not stop the others, and is offered again next time; each outcome is recorded through `jira_record_epic_link`, audited as the person, with the parent the epic had (`previous_parent`) kept so it can be put back (an undo screen is not built). The result names what moved and what did not. The next read of the tree (Sync or the daily check) shows the epics under the Initiative; Jira's search lags a couple of seconds behind the write. The GitHub twin (add sub-issues to a parent issue) is issue #458.
- **Epics coverage (2026-11-15, issue #464).** Incoming, Jira, Epics shows which open epics of the ticked projects (Settings, Integrations, Jira, Projects to check for epics) are linked to initiatives and which are not; see the decision `2026-11-13-tracker-initiative-level.md`. Read only; "List on initiative" records the epic key for the next Sync. GitHub twin: built (#465, `docs/04-GITHUB-SYNC.md`).
- **Read-only projects (2026-11-24, issue #656).** An admin can set a project read only for Jira (Settings, Integrations, Jira, Projects, "Access to Jira"). Nothing is then written to Jira for it (Sync, ownership, epic parents, closing removed issues are all refused, in the app and in the database); the epics listed on an initiative are read by key with their children and roll up delivery counts and Build Status. Switching to "can write" sends nothing by itself. See `docs/decisions/2026-11-24-jira-read-only-mode.md`. GitHub twin: #657.
- **Pull-in reads at once; the grid shows both levels (2026-11-15, issue #431, Ashu's test on Refinery89).** After a pull-in, `readPulledJira` runs the first half of Sync (statuses, tree, build dates) for the new initiatives, read only, creators and admins, and a failure never undoes the pull-in (the next Sync reads again). The grid's "Show issues" rows and the "Show these types" chips use the first two levels of the tree (an Initiative's epics with their stories and tasks nested; an epic's stories with sub-tasks); the Excel "Roadmap with epics" stays first-level. GitHub twin for the pull-in read: see the parity issue in the PR.
- **The mapping shows levels (2026-11-15, issue #431, slice 3).** On the Jira page the issue-type selects list every type with its hierarchy level ("Initiative · level 2, above Epic", "Epic · level 1", "Story · level 0", "Sub-task · sub-task"), highest level first, because a site can have two types with one name (the Refinery89 site has an "Initiative" at level 2 and another at level 0; the mapping stores the type id, so the data was never ambiguous). Under the row, a line says what the chosen initiative type means (above Epic: the epics come from this or any other Jira project and the build comes from them). The proposal is unchanged: the lowest level above Epic when there is one. Pulling in needs no change: Incoming lists the project's open issues of any type and a pulled-in Initiative gets its tree, Build Status and dates from its epics (slice 2). Not built yet: linking an existing Product Velocity initiative to an existing Jira issue (it is created through Sync with Jira or pulled in today), and the GitHub twin.
- **An initiative linked ABOVE Epic: a Jira Initiative (built 2026-11-15, issue #431, slice 2).** The tree read is the same (children of the linked issue, then their children), but at one level further up: the first level is the Initiative's **epics** (any issue type at hierarchy level 1: Epic, Workstream), which can sit in **other Jira projects** than the Initiative (proven on the Refinery89 site, `docs/08`); the second level their stories and tasks. Counting is unchanged (at the leaves; an epic with no children counts as one unit by its own status). What changes is what drives the build: **Build Status comes from the epics**, not from the Initiative's own status (all epics done = Done, none started = Not started, anything else = In progress; issues Jira did not classify are left out; with no epics Build Status is left as it is), **Start Building** is the earliest work start over the epics and everything below (the Initiative's own history is left out) and **Build Completed** is the latest epic resolution once every epic is done. The level of the linked issue is read once and kept (`item_jira_links.issue_level`, set by `jira_apply_link_level`); a status read leaves an issue above Epic alone (its own category is not applied), so the two never fight. Initiative Status is never touched. Jira's search lags about 2 seconds behind a write, so an empty child list right after a change is not an error: the next Sync or daily check shows it. Webhooks are per linked project, so an epic changed in a project that is not linked refreshes on Sync and in the daily check. The GitHub twin (a parent issue with sub-issues) is issue #453.
- **Children of a linked initiative (built, 2026-11-03):** an issue whose parent is the Jira issue of an initiative (and its sub-tasks) is part of that initiative's tree, not a new item: it is read into the initiative's Jira tab (read only), counted into Issues Total, Issues Closed and Delivery Progress %, and left out of the new-items lists and counts. Breakdown lives in the tracker; Product Velocity never creates epics or tasks, and a done child never makes the initiative done.
- **Hierarchy:** ignoring an epic or initiative-level issue ignores its children by default (shown as a suggestion the user confirms); pulling in a child whose parent is not pulled shows the parent as a plain reference.
- **Insights without noise:** ignored bugs can still be counted at team level for "bug share vs plan" (read-only counts, never individual metrics, rule 8); they never enter ranking.
- **Outbound is separate:** whether an item is pushed to the tracker stays a per-item action (today's "Push to GitHub"); the new part is the inbound choice. Pulled-in items follow the normal two-way rules.
- Audit: every state change records actor, source and reason, and can be undone (rule 5). Bulk pull-in or ignore is one undo step.
