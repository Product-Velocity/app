**Health, Initiative Status and Initiative Phase can be mapped to custom single-select fields on the Jira issue that is the initiative (a Jira Initiative, for example in RR), and CLAUDE.md rule 6 is amended for Initiative Status (issue #512).**

- **Why.** Jira's own status of an Initiative (Backlog, WIP Research, Done) means nothing for Build Status, which for an initiative linked above Epic comes from its epics (`2026-11-13-tracker-initiative-level.md`). Ashu wants to build custom fields on the Jira Initiative that mirror Product Velocity's own Phase, Health and Initiative Status, and keep them in step.
- **Rule 6 amended.** Before: "Initiative Status is set by people only, never by GitHub or Jira." Now: **Initiative Status may be proposed by a Jira custom select field, and only a person applies it** (Keep Jira in Sync with Jira, audited as the person, source UI, undoable). Nothing sets it silently, a closed ticket or a Jira status still never completes an initiative, and Build Status stays tracker-driven and not re-pointable. Setting Initiative Status to Completed still moves the phase to Completed (`docs/28-DECISION-GATES.md`), so the preview names the field in words.
- **Same for Health.** The dictionary said "never auto-set; GitHub signals only create suggestions". A change that comes back from Jira is the same kind of suggestion (a conflict card with Keep Product Velocity as the default), never an automatic change.
- **Initiative Phase only goes from Product Velocity to Jira** (Ashu did not choose between this and a gate-request suggestion; this is the safe default and is easy to extend). A phase moves at the decision gates and the database refuses a move past a gate (`PV006`), so Jira can never set it. Jira shows it; a phase edited in Jira is written back to Product Velocity's phase at the next confirmed Sync. A gate-request suggestion from Jira is **not built** and would be a new decision.
- **Mapping.** Per Jira-linked project, in Settings, Integrations, Jira, Field mapping, card **Initiative fields**: which custom single-select field, one Jira option for each Product Velocity value (an unmapped value is not sent and the preview says so; a Jira option no value stands for is left alone), and the direction. Fields and options come from Jira's create screen of the project's initiative issue type (`/issue/createmeta`), so a field that is not on the screen is not offered. Stored in `jira_select_map` (migration `20261118150830_jira_select_fields.sql`), written only by `jira_set_select_map` (a human workspace admin; never Claude, a service account or platform staff; audited).
- **Sync.** Product Velocity to Jira goes out only after the Sync preview and confirmation, like every other field. The three-way compare keeps the agreed Product Velocity value of each field in `item_jira_links.sync_base` (`sel_health`, `sel_initiative_status`, `sel_initiative_phase`). Only Product Velocity changed: it is sent. Only Jira changed: a conflict card (default Keep Product Velocity), nothing is overwritten or applied without a choice. Both changed: no default. Keep Jira calls `jira_apply_select_pull`, which takes Health and Initiative Status only (never Initiative Phase, never Build Status, never a commercial field), audited as the person. A choice made on an older Jira value is stale and writes nothing.
- **Rule 2 unchanged.** Health, Initiative Status and Initiative Phase are not commercial. They are added to the Jira outbound allowlist (`OUTBOUND_JIRA_FIELDS`) and the allowlist tests were extended: a hostile map cannot make a commercial field appear in a payload. The old test line that listed `initiative_status` among fields that never leave was removed with this decision.
- **Claude.** None of this is a Claude tool. Claude cannot change the mapping (the database refuses source MCP) and the existing item tools are unchanged, so the Help pages for Claude need no change.
- **Not verified here.** Jira cannot be reached from the cloud session. Everything is tested against a fake Jira and a real Postgres. What only a run on the RR site shows: the exact shape of `/issue/createmeta/{project}/issuetypes/{type}` on that site, that the custom fields are on the Initiative's screen, and that Jira accepts `{ "id": "<option id>" }` for them.
- **GitHub parity: built (issue #513, 2026-11-18).** The same flow on GitHub, on the single-select fields of the project's Projects v2 board: card **Initiative fields** under Settings, Integrations, GitHub, Field mapping (`board-select-card.tsx`), one board option per Product Velocity value, a direction per field, Initiative Phase only to GitHub. The mapping is stored with the board in `projects.github_board` (`selects`, no table change; `parseBoard` validates it and forces the phase to `to_github`), written by `saveGithubBoardSelects` (admin only, checked against the board's live fields and options). Push: `planBoardItem` writes the options. Compare: `compareBoardValues` has two more keys (`health`, `initiative_status`, hashes in `sync_base`), only for a slot set to both ways; a change on the board is a conflict on the board with Keep Product Velocity as the default, and Keep GitHub calls `github_apply_select_pull` (migration `20261118162616_github_select_fields.sql`: health and initiative_status only, never the phase, audited as the person), which is separate from `github_apply_pull` so that function was not replaced. `sync_base_valid` is replaced (create or replace, all eleven keys). Health and Initiative Status are read for the board only (`BOARD_ONLY_FIELDS`); a test pins that they never appear in the issue itself. **Not built on GitHub:** a phase edited on the board is not put back until the initiative's board values change for another reason (Jira puts it back at once); the board is not re-read for it.
