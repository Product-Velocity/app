**The Jira description is built from headed sections, like the managed block of a GitHub issue (issue #319).** Before this, Jira Sync sent only the Description field; Summary, Hypothesis, Artifacts and Files were GitHub-only (parity gap, `2026-11-03-tracker-parity.md`).

- **What is sent.** One Jira description with level-2 headings, in this order, a section with nothing in it left out: **Summary**, **Description**, **Hypothesis (IF / THEN / RESULTING IN)**, **Artifacts** (the initiative's links), **Files** (share links of attached files). The full PRD and other documents are still never sent (rule 2 and the existing test).
- **Compared both ways:** Name (the Jira summary), Summary, Description and Hypothesis, each with its own hash, Received, Conflicts and To send, "Keep Product Velocity" and "Keep Jira", exactly as GitHub. **Sent only:** Artifacts and Files; a change of the links rewrites the description (a hash of the two sections is kept in the sync base as `attachments`).
- **Reading back.** The description is cut at our headings, in order (top-level ADF headings of level 2, so rich content is not flattened). A Jira description **without our headings** (written before this, or typed in Jira) is read as the Description, so every existing issue keeps working. Text above our first heading is kept apart: never compared, kept when the description is rewritten.
- **Only what changed is rewritten.** A section that is not written keeps Jira's own content (a table, macro or mention survives); only a written section is replaced, and the preview says when that loses something Product Velocity cannot write back. The description is not written while one of its sections is still an unresolved conflict.
- **The one-time switch (decision 2).** An issue written before this has no sections. If the item has nothing for the new sections nothing happens (no mass rewrite). If it has a Summary or Hypothesis, or links or files, the next Sync lists it under To send ("The Jira description gets headed sections …"), keeps Jira's old text as the Description section, and writes nothing before the person confirms. A section Product Velocity has text for and Jira has none, never recorded before, is "send", not a conflict.
- **File links (decision 1, parity).** Share links of attached files that have a share link go into the Files section on Jira too. GitHub sends them only to private repositories; Jira has no repository visibility, so they are sent whenever the project's Files switch is on (default on). The login-free link means anyone who can open the Jira issue can open the file; the Sync preview names files that have no share link ("not in the description"). The switch exists per project to turn them off.
- **Field configuration.** New slots `jira.body.artifacts` and `jira.body.files` (switches, default on); Summary and Hypothesis are fixed, like Description, because the compare reads them. A switched-off section says so in the preview.
- **Migration** `20261104220831_jira_description_sections.sql` replaces two functions: `jira_apply_pull` (Keep Jira also takes Summary and Hypothesis, 4000 characters each) and `tracker_set_field_config` (the two new slots on its closed list; that function is from PR #318, which this change is stacked on).
- **Known limit, same as GitHub:** a Product Velocity text that itself contains a level-2 heading with exactly one of our section names, in the right order, is read as the start of that section.
- **Not verified here:** a real Jira description round trip (ADF headings, the section split on a real site), and that files links open for the Jira users. Tested against the fake Jira.
