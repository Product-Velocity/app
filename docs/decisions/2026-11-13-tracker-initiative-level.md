**A Product Velocity initiative links to one tracker issue that sits above the epics (a Jira Initiative, or a GitHub parent issue), and Product Velocity reads initiative -> epics -> stories and sub-tasks as one tree (issue #431).** Why: a business roadmap item is delivered by several epics. Pulling every epic in as its own initiative would count the same item twice in the roadmap, the stack rank and the velocity numbers, and Initiative Group is one flat label, so it cannot say "this epic delivers R-37". The grouping belongs in the tracker, where the delivery structure already lives.

- **Where the grouping lives.** In Jira: the Jira Initiative level (hierarchy level above Epic; Ashu confirms the plan and hierarchy on the Refinery89 site). Epics are children of the Initiative; their stories and sub-tasks stay under the epics. Do not convert an existing epic into an Initiative (its stories would be orphaned); create the Initiative and put the epics under it. A roadmap item with exactly one epic may link that epic directly (works today). In GitHub: a parent issue with sub-issues, which the roll-up already reads at all levels.
- **What Product Velocity reads.** The whole tree below the linked issue, read-only on the Jira tab, counted into Issues Total, Issues Closed and Delivery Progress % without double counting. **Epic status drives Build Status, Start Building and Build Completed** (status category, as in `2026-11-11-tracker-build-dates.md`). Stories and tasks only add counts; no story or task level view is built for this. The epics under a linked Initiative are never offered as new items.
- **Pull-in, link and the level choice.** The Jira project link already says which of that project's issue types is the Product Velocity initiative, the epic and the task (`2026-11-02-jira-project-link.md`). **"Initiative" is added as one more choice for the initiative level; the Epic and Task options stay exactly as they are.** "Initiative" is also added to the Incoming level choice. A Jira Initiative can be linked to an existing Product Velocity initiative as well as pulled in as a new one.
- **Where the Initiative and its epics live: both layouts are supported (Ashu, 2026-11-14, after Paulina Novillo's note on the Jira side).** (a) **Same project:** the Initiative and its epics are in one company-managed Jira project. (b) **Split:** the Initiative is in one project and its epics are in other projects. Facts from the Jira manager (2026-11-13): R8P is a team-managed project with a fixed hierarchy (Epic, then Story/Task/Bug, then Sub-task), so no work type can be added above Epic there; Initiative belongs to the company-wide hierarchy and can only be created in a company-managed project; an R8P epic can still take an Initiative from a company-managed project as its parent; and one Initiative can hold epics from different projects (the cross-team case). The two options she gave: a separate company-managed project for the Initiatives (works now, R8P unchanged; **chosen direction, to be confirmed by Ashu in Jira**) or migrating R8P to company-managed (slow, not needed for Product Velocity). **The Initiative's project is the one the Product Velocity project links to; the epics' projects are not linked and not pulled in: their issues are only read as children of the Initiative** (the tree read asks for `parent in (...)` with no project filter, so this should work across projects; to be proven in J2). A Product Velocity project (the roadmap grouping, an initiative's home project) and a Jira project stay independent things.
- **Epic keys at creation, built (2026-11-15).** On an initiative's Jira tab a person lists epic keys (any project); Sync with Jira previews them and, after confirmation, creates the Initiative if needed and sets each epic's parent to it. It writes only the parent of the epic (rule: tracker-owned fields stay the tracker's), never silently (preview and explicit confirmation, rule 3), an epic that is already under another Initiative is shown as a move and its old parent is kept, one epic belongs to one initiative, and only epics (level 1) are accepted. Not built: an undo screen for a moved epic, orphan epics (a list of epics with no Initiative parent), and the GitHub twin (#458).
- **Tree read, first slice built (2026-11-15).** For an initiative linked to an issue above Epic: **Build Status** from its epics (all done = Done, none started = Not started, otherwise In progress; unclassified left out; no epics = left as it is); **Start Building** = the earliest work start over the epics and below, the Initiative's own history left out; **Build Completed** = the latest epic resolution once every epic is done; roll-up counts at the leaves as before. The epics are the first level of the tree whatever their type (Epic, Workstream), from any project, shown in order by project then number. The level of the linked issue is kept on the link (`item_jira_links.issue_level`), and a status read leaves an issue above Epic alone. Not in this slice: linking an existing Product Velocity initiative to an Initiative, the level choice in the project mapping and Incoming, orphan epics (the next slices). GitHub parity is issue #453.
- **J2 outcome so far (2026-11-14/15, details in `docs/08`).** The Initiative level exists on the Refinery89 site; one Initiative in a company-managed project holds epics from two projects, including the team-managed R8P, and Product Velocity's own `parent in (...)` query reads them and their children; an Initiative can be created through the API, an epic of another project can be linked to it and removed again. The Initiative project (RR) has no Epic type, so the layout there is the split one. **Jira's search lags about 2 seconds behind a write (proven 2026-11-15):** an empty child list straight after a parent change is never an error; the next read shows it, and a read right after Product Velocity's own write waits a few seconds and asks again.
- **Cross-project read: what J2 must prove, and what it means if it does not hold.** (1) `parent in (INIT-1, ...)` returns the epics (and their stories and sub-tasks) from other projects. (2) **Webhooks are filtered to the linked project (`project = KEY`), so a status change of an epic in an unlinked project does not arrive by webhook.** Those epics refresh only when Sync with Jira runs and in the daily check. Decide after J2: accept that, or let a Product Velocity project name extra Jira projects for the webhook filter only (no pull-in, no mapping). (3) **Permissions:** the Jira sign-in Product Velocity uses must be able to browse every project that holds epics under the Initiatives; an epic it cannot see is missing from the roll-up, so the Jira tab says when a child count may be incomplete rather than showing a quiet undercount. (4) The Initiative-level issue type, its parent link and the write-back of "create an Initiative, set an epic's parent" (J4) on the real site.
- **Pull in and own stays, at the Initiative level too (Ashu, 2026-11-14).** Today whatever sits at the level of a Product Velocity initiative (an epic, with the usual mapping) can be pulled in and then either followed read-only or **owned by Product Velocity** (link mode "push": Product Velocity sends the allowlisted fields after a preview and a confirmation). That does not change, and it **extends to Jira Initiatives** (and, for parity, to the GitHub parent issue): when the project's mapping says the Product Velocity initiative is the Jira Initiative, a pulled-in Initiative can be followed or owned in the same way, and "create in Product Velocity, send to Jira" creates the Initiative. **Everything below the initiative level (epics under an Initiative, their stories and sub-tasks) is read-only** and never offered as new items. A project has one initiative level at a time: with the mapping set to Epic (today), epics are pulled in and owned as now; with it set to Initiative, epics are the read-only children.
- **Who owns what.** Product Velocity owns the lifecycle fields (Initiative Phase, MoSCoW, Stack Rank, Initiative Status and the rest of the initiative's fields: description, tags, links, key results). The tracker owns the delivery structure, Build Status and delivery progress, which stay read-only in the app (rule 6). **A lifecycle field changed in Jira may come back into Product Velocity in the two-way sync, but never silently: the sync always flags it** (a change-from-tracker card, like a conflict, with the old and new value). Initiative Status is still set by people only; a closed epic never completes the initiative.
- **Two ways to create an initiative with its epics (both supported).** (1) Create the initiative in Product Velocity, send it to Jira (preview and explicit confirmation as always), connect the epics in Jira, sync again. (2) Create the Initiative in Jira, connect the epics there, and pull it in on the next sync.
- **Orphan epics (second slice).** A list of Jira epics that have no Initiative parent. For each: link it to an existing Product Velocity initiative, or create a new initiative from it, and send the result to Jira after the preview and an explicit confirmation (create the Jira Initiative, set the epics' parent). Claude may propose the matches as a draft; a person accepts (rules 3 and 4).
- **The fresh start is Ashu's to trigger.** The epics already pulled into R89 Publisher stay exactly as they are. **Clearing them is done only when Ashu asks for it explicitly, in a later request; nothing built under #431 deletes, archives or relinks production data.** The plan is: finish the Jira Initiatives (including the ones for the epics with no roadmap match, e.g. technical debt), link them to the Product Velocity initiatives in Jira, then clear and re-sync so the links are right from the start.
- **The report.** A "Roadmap with epics" Excel download, built through the report engine (audience profile, server-side field filtering), matching sheet "Roadmap v3" of `Refinery_Roadmap_v31.xlsx`: one row per initiative with its epics as grouped child rows (Excel outline level 1), frozen header row, filter, the same column order. Epic rows carry their own columns (key, name, Jira status and status group, assignee, dates, last updated, link confidence). Review Flags and Hugo Comments exist only in that workbook; they are not Product Velocity fields and are left out unless Ashu adds them as fields.

- **Parity.** Built for GitHub and Jira in the same flow. The only exception to record in the PR is that the hierarchy-level check is Jira-only.
