**A Product Velocity initiative links to one tracker issue that sits above the epics (a Jira Initiative, or a GitHub parent issue), and Product Velocity reads initiative -> epics -> stories and sub-tasks as one tree (issue #431).** Why: a business roadmap item is delivered by several epics. Pulling every epic in as its own initiative would count the same item twice in the roadmap, the stack rank and the velocity numbers, and Initiative Group is one flat label, so it cannot say "this epic delivers R-37". The grouping belongs in the tracker, where the delivery structure already lives.

- **Where the grouping lives.** In Jira: the Jira Initiative level (hierarchy level above Epic; Ashu confirms the plan and hierarchy on the Refinery89 site). Epics are children of the Initiative; their stories and sub-tasks stay under the epics. Do not convert an existing epic into an Initiative (its stories would be orphaned); create the Initiative and put the epics under it. A roadmap item with exactly one epic may link that epic directly (works today). In GitHub: a parent issue with sub-issues, which the roll-up already reads at all levels.
- **What Product Velocity reads.** The whole tree below the linked issue, read-only on the Jira tab, counted into Issues Total, Issues Closed and Delivery Progress % without double counting. **Epic status drives Build Status, Start Building and Build Completed** (status category, as in `2026-11-11-tracker-build-dates.md`). Stories and tasks only add counts; no story or task level view is built for this. The epics under a linked Initiative are never offered as new items.
- **Pull-in and link.** "Initiative" is added to the Incoming level choice. A Jira Initiative can be linked to an existing Product Velocity initiative as well as pulled in as a new one.
- **Who owns what.** Product Velocity owns the lifecycle fields (Initiative Phase, MoSCoW, Stack Rank, Initiative Status and the rest of the initiative's fields: description, tags, links, key results). The tracker owns the delivery structure, Build Status and delivery progress, which stay read-only in the app (rule 6). **A lifecycle field changed in Jira may come back into Product Velocity in the two-way sync, but never silently: the sync always flags it** (a change-from-tracker card, like a conflict, with the old and new value). Initiative Status is still set by people only; a closed epic never completes the initiative.
- **Two ways to create an initiative with its epics (both supported).** (1) Create the initiative in Product Velocity, send it to Jira (preview and explicit confirmation as always), connect the epics in Jira, sync again. (2) Create the Initiative in Jira, connect the epics there, and pull it in on the next sync.
- **Orphan epics (second slice).** A list of Jira epics that have no Initiative parent. For each: link it to an existing Product Velocity initiative, or create a new initiative from it, and send the result to Jira after the preview and an explicit confirmation (create the Jira Initiative, set the epics' parent). Claude may propose the matches as a draft; a person accepts (rules 3 and 4).
- **The fresh start is Ashu's to trigger.** The epics already pulled into R89 Publisher stay exactly as they are. **Clearing them is done only when Ashu asks for it explicitly, in a later request; nothing built under #431 deletes, archives or relinks production data.** The plan is: finish the Jira Initiatives (including the ones for the epics with no roadmap match, e.g. technical debt), link them to the Product Velocity initiatives in Jira, then clear and re-sync so the links are right from the start.
- **The report.** A "Roadmap with epics" Excel download, built through the report engine (audience profile, server-side field filtering), matching sheet "Roadmap v3" of `Refinery_Roadmap_v31.xlsx`: one row per initiative with its epics as grouped child rows (Excel outline level 1), frozen header row, filter, the same column order. Epic rows carry their own columns (key, name, Jira status and status group, assignee, dates, last updated, link confidence). Review Flags and Hugo Comments exist only in that workbook; they are not Product Velocity fields and are left out unless Ashu adds them as fields.
- **Spike first.** Anything above Epic is **[SPIKE J2]** (parent link and JQL for children of an Initiative on the Refinery89 site) and write-back is J4. The result is recorded in `docs/08` before the read and the report are built; the report itself can be built on the current data in the meantime.
- **Parity.** Built for GitHub and Jira in the same flow. The only exception to record in the PR is that the hierarchy-level check is Jira-only.
