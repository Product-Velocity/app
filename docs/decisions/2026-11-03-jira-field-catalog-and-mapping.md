**The Jira field catalog and the field mapping per project link (issues #69, #70).** On Settings, Integrations, Jira, an admin of a linked project sees a "Fields" section: every field of the Jira site (id, name, system or custom, kind, role hint, filled count out of a sample of the project's newest 100 issues) and maps chosen Jira fields to existing PV fields, read only or two-way. Unmapped fields stay in the list and are ignored. **The 170-field dictionary does not grow.** Saving a mapping writes nothing to Jira and changes no initiative: reading mapped values and sending them belong to the read and write sync sessions.

- **Storage.** `jira_field_catalogs` (cache, one row per link, written by the server only, read by human admins only, not audited like `jira_reads`) and `jira_field_mappings` (per link: Jira field **id**, name, kind, custom flag, PV field, direction; unique per Jira field and per PV field; members can read it, nobody writes it directly; audited). Written only by `jira_set_field_mapping` / `jira_remove_field_mapping` (human admin; not Claude, service accounts or platform staff). Migration `jira_field_mappings`.
- **Cache lifetime.** No automatic expiry: field lists change only when a Jira admin adds or renames a field, and a refresh costs two Jira calls. The page shows when the list was read, flags it after 7 days, and has "Refresh the list". A refresh that fails keeps the old list and shows the reason; "sign in again" is shown, never retried.
- **One rule, two places.** `packages/domain/src/jira-field-mapping.ts` (`validateJiraMapping`, used by the page and the server action) and the SQL `jira_mapping_check` (used by the function) apply the same table. A database test compares them for every dictionary field x every Jira kind x both directions x system and custom ids.
- **What may be mapped (a whitelist, everything else is refused).** Planned Start, Target G2M Date (G2M Date est) and MoSCoW (the only ones that may be two-way, because they are exactly the fields the Jira outbound allowlist `OUTBOUND_JIRA_FIELDS` already sends; a test ties the lists together); read only: Effort, Horizon, Theme, Focus Area, Estimate low/high (weeks), Tags, Contributing Teams, Assignees. Kinds must match (number to number, date to date, text to text, labels to labels or multi-select, select to select, team to Contributing Teams, people to Assignees); the UI offers only valid choices and says why a field has none.
- **Refused, with a reason the admin reads.** Commercial and person-only fields (value, confidence, customers, decisions, key results, outcomes, markets, rank), alignment and crowd results, tracker-driven fields (Build Status, delivery progress, PR/CI), Initiative Status (people only), calculated and system fields, any Jira status, resolution or computed field, and Jira's title and description (Sync already keeps those in step).
- **Decision for Ashu to confirm.** The brief says commercial fields can never be mapped two-way or outbound. I also refuse reading them **from** Jira, so that a Jira edit can never set Value, Decision or Stack Rank (person-only). Loosen it by adding a field to the targets table in both places.
- **Decision for Ashu to confirm.** No suggestion for Story points: Effort is a T-shirt size and the estimates are in weeks, points are neither. Suggestions exist only for Start date, Due date, Team, Labels and Assignee, are shown as hints and are never applied.
- **How to read and write each kind** (`field-values.ts`: `readJiraValue`, `toJiraValue`). Team, Parent and Sprint used to be "other"; the catalog now tells `team` and `parent`. People are read as the account id only (never an email); a value that does not fit gives null and is skipped; Jira text is only copied, never interpreted. Team, parent, sprint, people and unknown objects are read only.
- **For the two sync sessions.** `loadFieldMappings(supabase, linkId)` (`apps/web/src/lib/atlassian/field-mappings.ts`) returns `{ all, readable, writable, byJiraField, byPvField }` as the signed-in person; each row is validated again and a row the rules no longer allow is dropped. The read side uses `readable` with `readJiraValue(m.jiraKind, issue.fields[m.jiraFieldId])`; the write side uses `writable` with `toJiraValue({ id, custom, kind }, item[m.pvField])` and must still read items through `OUTBOUND_JIRA_FIELDS`.
