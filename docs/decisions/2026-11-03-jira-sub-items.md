**The children of a Jira-linked initiative are read into the initiative, like GitHub's epics and tasks (issues #67 and #71).** Found on a real test workspace: an initiative linked to the Epic SCRUM-12 has six children in Jira (Feature and Task, parent = SCRUM-12), and pulling issues in made each child a separate initiative (R-15 to R-20, since moved to the Trash). With GitHub the children of the tracking issue are a read-only sub-table of the initiative and feed its delivery progress. Jira now does the same. Breakdown lives in the tracker (CLAUDE.md, docs/04): Product Velocity never creates epics or tasks.

- **What is read.** For every initiative linked to a Jira issue: the children by Jira's `parent` field (`parent in ("KEY", …)`, keys validated by a regex, at most 100 parents per call, token paging like the open-work read) and ONE more level, the children of those children (sub-tasks). Per issue: key, title, type, level (1 child, 2 sub-task), parent key, status name, status CATEGORY, assignee display name, Jira's updated time and the order Jira returned them in. Nothing is written to Jira. Titles and names are cleaned and cut (text from Jira is data).
- **Where it is stored.** `item_jira_tree` (migration `jira_sub_items`), the Jira twin of `item_issue_tree`: tenant RLS with the fast policy and an index starting with `tenant_id`, the platform read-only guard, written only by the service-role function `jira_apply_tree` (source "system"), which replaces the initiative's rows, compares before writing (an unchanged tree adds no audit rows) and writes the roll-up. Rows of the tree are derived data and are not audited one by one; the item columns it feeds are, with old and new value.
- **The roll-up (one counting rule, `jira-tree.ts`).** Counted at the leaves: a child counts only while it has no sub-tasks. A child in the **done category** is closed (status names mean nothing: in Ashu's workflow "To Do", "In Progress" and "Testing" are all in the in-progress category). Issues Total, Issues Closed and Delivery Progress % are filled from it; progress stays empty while there is nothing to count, and an empty tree never writes zeros over an empty roll-up. **A closed child means the build is progressing, never that the initiative is complete** (rule 6): Initiative Status and Build Status are never set from the tree.
- **When it runs.** After the status read, in the same three places: the Sync dialog start (for the selected initiatives), the first step of Sync that reads new items (so children are left out of the list before it shows), and the daily check (`/api/cron/jira`). A failure of the tree (Jira refused, too many children, the database function not applied yet) is returned and logged and never fails the status read; **ReconnectNeeded propagates** and is never retried. A tree is applied only when it was read completely: a batch with more than 20 pages of children fails before anything is written, and an issue Jira refuses (400) keeps the tree it had instead of being replaced by an empty one. Limits: 500 issues per initiative.
- **Children are not new items.** `jira_issues.child_of_item` (nullable) is set by `jira_apply_tree` for the light record of every issue in a tree (an issue already pulled in is left alone) and cleared when it leaves the tree, so it is offered again. The Jira step of the Sync dialog, its count, the issue list of the Jira settings page and `jira_issue_counts()` all leave out `child_of_item is not null`. **`jira_issue_counts` is replaced by this migration** (`create or replace`, same columns); no other open branch replaces it (checked 2026-11-03).
- **Before the migration is applied.** The migration is applied to the Supabase project by hand. Until then nothing breaks: the list filters fall back to the unfiltered query when the column is missing (`child-filter.ts`), the panel reads the tree in its own query and shows an empty list when the table is missing, and the tree refresh counts as failed without touching the status refresh. A missing column once made a whole project link look empty; this is why every new read is separate and tolerant.
- **Shown.** The initiative's Jira tab has a read-only table: Issue (the key links to the Jira browse page), Title, Type, Status (name and category in words), Assignee; sub-tasks are indented under their parent. The line above it says "n of m issues done" and that a done issue is not a done initiative. Assignee names appear as data in the table only: no counts or charts per person (rule 8).
- **Not in this slice.** A third level below sub-tasks; children of an issue that is not linked to an initiative; hiding or restoring a child as its own initiative from the tree; webhooks (the list is as fresh as the last Sync and the daily check); a "Received" line in the Sync dialog for tree changes.
- **Not verified here.** Jira cannot be reached from the build environment; everything is tested against a fake Jira. What only a run on a real site shows: that `parent in (...)` returns both Epic children and Sub-tasks on the Refinery89 workspace, the 400 Jira gives for a key that does not exist, and the assignee field being returned for these issues.
