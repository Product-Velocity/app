**A Product Velocity project linked to a Jira project can be set "Read only: listen to Jira". Nothing is then ever written to Jira for it; the epics listed on an initiative are read by key and their status rolls up.** An admin can switch the project to "can write" later; switching sends nothing by itself.

- **Where.** Settings, Integrations, Jira, Projects: the row of each project gets "Access to Jira" (Product Velocity can write / Read only: listen to Jira) between the Task type and Save, saved with the same Save. Stored as `jira_project_links.read_only` (default false: existing links change nothing). Changed only by a human workspace admin through `jira_set_project_read_only` (never Claude, never a service account), audited by the table's audit trigger. Switching to "can write" shows a note with the number of initiatives the next Sync would offer to create; it is confirmed by the Save and still asks again at Sync.
- **What is blocked while read only.** Sync with Jira (the preview and the confirmed send both stop before Jira is read; the card says why), taking ownership (database trigger, error `PV013`), the epic-parent write at Sync (`autoLinkEpics` does nothing; a request cannot be marked `linked`, trigger `PV013`), closing the Jira issues of removed initiatives (`jira-removed-engine`). Tests: `packages/db/tests/jira-read-only.test.ts`, `jira-sync-engine.test.ts` ("a project that is read only") and `epic-tree.test.ts` (only search paths are produced).
- **What is read.** The epic keys listed on the initiative (Jira tab, the Epics tab's "List on initiative", or Claude's `request_jira_epics`: unchanged, they only record) are read by key with their children, at Sync with Jira and in the daily check. Level 1 of the existing read-only tree = the listed epics (their parent key is their own key, there is no Jira issue above them), level 2 = their children; delivery counts are counted at the leaves; Build Status comes from the epics (all done = Done, none started = Not started, otherwise In progress), compare before write, audited with source `system` (`jira_apply_epic_tree`). The initiative needs no Jira issue of its own. A closed epic never completes the initiative (rule 6); Initiative Status is untouched. Keys Jira does not return or that are not epics are said on the Sync card and in the Jira tab check; a failed read never empties a tree.
- **Epics outside the linked Jira project.** Webhooks cover the linked project only, so those epics refresh at Sync and in the daily check (as in `2026-11-13-tracker-initiative-level.md`). The sign-in must be able to browse their projects.
- **Switching to write later.** The listed keys stay as `pending` requests; the next Sync with Jira previews them as in `2026-11-18-epic-ids-link-at-sync.md`. Tree rows read while read only are replaced by the normal read once the initiative has its Jira issue.
- **Not built.** Start Building and Build Completed from the epics' history (they need a Jira link; the read-only tree gives counts and Build Status only); showing each epic's status next to its key on the Jira tab; per-initiative (not per-project) mode; the GitHub twin (#657). Jira webhook registration is an app-level subscription to read events, not a write to a project's issues, and is unchanged.
- **Follow-up (issue #660, 2026-11-24, after the first run).** The Jira tab of an initiative in a read-only project shows "n epics · m child issues" and how many are done, with the epics and their children (status, assignee, links) from the stored tree; the key list and the tree scroll inside the panel; each project row on the Projects table shows "Last saved" (`jira_project_links.updated_at`) and a "Saved" chip for a minute after saving.
- **Parity.** Exception: Jira first, the GitHub twin is issue #657.
