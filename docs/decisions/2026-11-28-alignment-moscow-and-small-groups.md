**MoSCoW becomes an alignment method, the vote shows a collapsible card, coins get project defaults, and a group's own result can be shown to that group.** Issue #746. Nothing here is built yet; slices are in the request file.

1. **MoSCoW is a fourth method (`moscow`).** One of Must, Should, Could, Won't per initiative. **No "no opinion"** (Ashu: stakeholders would only vote on their own items), so a ballot needs a choice for every initiative in the session before it can be submitted.
2. **The final MoSCoW is set by an admin** (workspace or project admin) from the result, the way the vote is applied to the Stack Rank (#394, #397): review step, a reason where the final value differs from the vote's, one audit entry, undo while nothing has moved, never Claude or a service account (`PV004`). Only the `moscow` field changes. **Built (slice 2).** Every initiative in the vote starts ticked with the suggestion as its new value, an existing value is overwritten only for the ones left ticked (the review says how many), and the reasons are admin-only. Only admins can read the record; a creator who opens the page sees the suggestion but not the apply form.
3. **Ties go cautious.** *Read as:* the lower commitment wins: a tie between Must and Should becomes Should, Should and Could becomes Could, Could and Won't becomes Won't. Tied items are flagged contested. If Ashu meant the opposite, it is one line in the scoring function.
4. **Coins: the session already stores `coins_total` (default 100) and `coins_max_per_item` (default 30) and the admin can set both per session.** What is new is a **project default** for both, copied into a new session when it is created and still editable until the session opens. Settings stay locked once a session is open (PV009), so a later change to the project does not alter a running vote.
5. **Everything the admin selects for the session is in the vote.** No readiness check, no filter. (The planning document's "no estimate basis, no vote" rule is not enforced.)
6. **Collapsible card for voters.** Name, summary and value proposition stay visible. A closed-by-default "More" control opens a card with **Business Line, Business Value (12m) and Effort**. The participant-safe snapshot taken when the session opens gets these three columns. Business Value is commercial: which fields voters see is a per-session setting, default on for these three, and the admin can untick any of them before the session opens.
7. **A group's own result can be shown to that group (reverses part of docs/19 section 5 and rule 7, for sessions that switch it on).** A per-session toggle "Show each group its own result", **default off**, locked when the session opens. When on, a participant sees the result of their own group even with fewer than 5 voters, never another group's. *Read as:* "visible to the group" means to that group's members only. Consequences, written here so they are not a surprise: with a group of 1 or 2 people the group result is their own answer or nearly; the joint result and the admin names path do not change; the consent wording changes and gets a new version, so earlier consents do not cover it; the results page tells the admin before opening that groups under 5 will see their own result. `docs/19` and `CLAUDE.md` rule 7 are amended in the slice that builds the toggle, not before.
8. **Out of scope:** capacity and planning cycles, a combined MoSCoW-plus-points ballot. Round 2 of a vote is a new session named "round 2".
