**One list on the Jira tab, and the Jira label names the initiative by its Initiative ID.**

- **One list.** When Product Velocity owns the initiative, the Jira tab shows the epics grid only (plus the "n of m issues done" line). The second "Issues under …" table repeated the same rows and is shown only for a read-only (follows) initiative, which has no grid. So that nothing is lost, the grid now also lists epics found under the initiative's issue that nobody listed (made in Jira): they read "In Jira", have no Check or Remove, and their children follow. Status is Jira's and stays read only everywhere (rule 6); nothing here writes to Jira.
- **The label is the Initiative ID.** `pm:item/<hash>` becomes `pm:item/R-102` (the prefix stays configurable in stealth mode). It was not decoration: it finds an issue again after a create whose answer was lost, so it stays and now also stays on the issue at every Sync (before, the next Sync removed it as one of our labels). An item without a plain code (letters, digits, `.`, `_`, `-`, up to 32) keeps the hash. **Existing issues:** the next confirmed Sync swaps the old hash label for the ID label and keeps people's own labels; that one update shows in the preview.
- **Why it is safe to use the ID.** The ID is a system code, not a commercial field (field dictionary: "shown in issue body as backlink"). Known limit, not verified against how connections are shared: if two workspaces ever send to the same Jira project, the same ID in both would find the other's issue on a lost-answer recovery.
- **Assignee (Ashu, 2026-11-27, answered in chat): the Product Manager is the Jira assignee of a NEW issue only, matched by email, and sending the email to Jira's user search is fine.** This reverses "Assignee not built" (2026-11-16) for this one case. At a confirmed create, the server reads the Product Manager's email (a workspace member only), asks Jira's user search (a read) and sets `assignee.accountId` only when exactly one active Atlassian user matches (an email Jira hides is accepted only when the search finds exactly one user). Never again after the create: Sync does not read, compare or write the assignee, so people reassign freely in Jira. No match, no Product Manager, no permission to browse users or a refusal by Jira (field not on the screen) leaves it empty and the preview or result says why; the issue is always created. The email is never logged, shown, stored or put in a note; no Jira account id is stored. Jira only; GitHub already has its own two-way Assignees column (parity line on the PR).
- **Initiative Phase label (Ashu, 2026-11-27): on by default, both trackers.** `pm:phase/<phase>` (Discover, Define, Build, Test, Experiment, Roll-out, Completed become `pm:phase/discover` … `pm:phase/roll-out`), the same shape and switch as the Planned Quarter label (field configuration, per project; prefix renamable in stealth mode). It is sent only; a tracker never sets the phase (rule 6). The existing `pm:define` review label stays as it is. Needs migration `phase_label_default_on` (the allowed-slot list of `tracker_set_field_config`). Field dictionary row Product Manager updated (Jira assignee on create).
- **Assignee, follow-up (issue 742, 2026-11-27).** The Product Manager column holds a person of the people directory (a member's person id is their user id). A person without an account, or without an email, was not found by the first version, which read accounts only: on R-113 the preview said the email could not be read. Now the person's own email, else the email of the account behind them, is tried first; with no email Jira finds a user for, the person's exact name is tried, and a user is accepted only when exactly one active Atlassian user has exactly that display name (accents and case ignored); several or none leave the assignee empty. The preview says "matched by name because no email was found: check it is the right person" before anything is written. Still created only, never changed afterwards.
