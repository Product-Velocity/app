**GitHub and Jira settings are split into two sections, then get a field configuration (same flow on both, `2026-11-03-tracker-parity.md`).**

## 1. The split (built)
- **Two routes, one tab bar.** `/settings/integrations/<tracker>` is **Connect and configure**; `/settings/integrations/<tracker>/logs` is **Sync logs**. The bar is one component (`components/tracker-tabs.tsx`) with the same two labels on GitHub and Jira, `aria-current="page"` on the open one. Routes (not client tabs) so each section has its own address, can be linked from a notice, and the logs page loads nothing heavy (no Jira calls).
- **Connect and configure** holds Status (connect, test connection, sign in again, disconnect), Projects, GitHub repositories and boards, the Jira issues waiting for a decision, and (slices 2 to 4) the field configuration. **Sync logs** holds the "what happens by itself" text, Live updates, Check now, Last check, the recent events with Run again, and a link to the latest connection test.
- "Check now" and "Run again" return to **Sync logs** with their result notice. The Jira dev harness (`/dev/jira`, `/dev/jira/logs`) has both sections for Playwright and axe.

## 2. Read the tracker's fields (built)
- **Jira:** every field of the site by id (system and custom: names are not unique), kind and custom or system, the options seen on the sampled issues for select fields (the site's full option lists need a call per field context, so the catalog says "seen in the sample"), a fill rate over the 50 most recently updated issues of the linked project, the priorities and the project's issue types. `readJiraCatalog` (reads only).
- **GitHub:** the organisation's issue fields (`GET /orgs/{org}/issue-fields`; needs the App permission "Issue fields", read, docs/08 S3b: without it the catalog says so and nothing fails), the built-in issue fields, the fields of each linked Projects v2 board, the labels and milestones of the projects' default repositories (three at most), and the organisation's issue types. Fill rates are not sampled on GitHub (the catalog says "not sampled"). Three new read-only calls on the source-control interface: `listIssueFields`, `listLabels`, `listMilestones`.
- Every part has its own "could not be read just now" state; the other parts still show. A tracker field that is not mapped stays in the catalog and is ignored.

## 3. The default mapping and what a person can change (built)
- **One table per project, the same on both trackers:** Product Velocity field | direction | where it goes by default | your setting | Reset. All 170 dictionary fields are covered (`tracker-fields/slots.ts`, `mappingRows`): the rows that can change come first, every other field follows in a folded list with the reason. Directions: *Product Velocity to tracker*, *both ways*, *tracker to Product Velocity, read only*, *not synced*, *never synced*.
- **The defaults are derived from the code that Sync runs** (Jira: `outbound.ts`, `jira-sync-core.ts`, `jira-sync-engine.ts`; GitHub: `packages/github/src/outbound.ts`, `board.ts`, `push.ts`), and tests pin them: with nothing saved the Jira map, the Jira payload, the GitHub issue (title, labels, milestone, issue type, body, hash) are identical to before this change.
- **A "slot" is one thing Sync can do for a field.** The list of slots is closed (`SLOTS`). Three kinds: *fixed* (cannot change, with the reason: Jira summary and description, the GitHub title, code and the three compared sections of the managed block, because the two-way compare reads them), *toggle* (send or do not send: the five `pv:` labels on both trackers; GitHub also the milestone, the organisation issue type and the Artifacts and Files sections) and *field* (point at another tracker field: Jira due date, start date, Theme and the priority per MoSCoW value; GitHub board Priority, Group, Due date and Size).
- **Where a choice is saved (extend, not replace):** Jira start date, Theme and priorities stay in `jira_project_links.field_map` (`jira_set_field_map`), so existing saved maps keep working; everything new is in the new table `tracker_field_config` (migration `20261103233355_tracker_field_config.sql`), written only by `tracker_set_field_config`. The Jira form saves both in one click (field map first, then the switches). The GitHub board fields stay in `projects.github_board` and are changed in the existing **Project boards** card, which already reads the board's own fields and offers "Don't write"; the new table lists their current value and links there, so there is one editor per field, not two.
- **Scope is the project.** A project has exactly one tracker and so one connection; storing the project (not a connection id) keeps a setting valid after a reconnect that replaces the connection row. There is no workspace-wide default layer (YAGNI); a person with several projects sets each.
- **Switching a label off removes it:** Sync already treats the `pv:` labels as Product Velocity's own (it adds those that apply and removes those that do not), so a label switched off disappears from the issues at the next confirmed Sync, and the preview lists it. Labels people added are never touched.
- **Reset to default** per row and for all (a form post, no script).

## 4. Hard boundaries (built, tested)
- **Never synced rows (rule 2):** value, confidence, customers (requests, target, live), decisions and who/when, cost of not doing, key results, realised value, outcomes and the other commercial fields (`NEVER_SYNCED`, 33 fields) are shown as "Never synced", cannot be edited, have no slot, and the outbound allowlist tests were extended: a custom or hostile configuration (re-pointed fields, every switch off, slot names of commercial fields) cannot make a non-allowlisted field appear in a Jira or GitHub payload. The database refuses any slot that is not on its closed list (so a stored row cannot name one either), and a test fails when the list in the app and the list in the migration differ.
- **Tracker-driven fields (rule 6)** (Build Status, delivery progress, issue and PR counts, CI, the board's status, iteration and target date, and for Jira the status category and the children counts) are listed as "read from the tracker, read-only in the app" and are **not re-pointable**: a test checks that every one is non-editable in the dictionary and has no slot. **Initiative Status** is never set from a tracker (a test checks it is not in any tracker-driven list).
- The 170-field dictionary does not grow; tracker fields without a Product Velocity field stay in the catalog and are ignored.
- **Who can save:** a human workspace admin only. The database function refuses Claude (source MCP), service accounts, creators, admins of another workspace and platform staff (they are not members; the platform read-only guard is on the table). Every change is audited (actor, source, time, old and new value) by the table's audit trigger; only rows that differ are written. The server action also refuses platform staff and checks every field id against the fields the site reports **at save time** (it must exist, be of a compatible type, and not be used by another Product Velocity field); when the site cannot be read, the switches still save and choosing another field is refused with a message.

## 5. The engines use it (built)
- **Jira Sync** (preview and confirm both go through `evaluate`): the saved field map and the saved settings make the map the payload builder reads; the custom fields it names are checked against the site's fields (one read per site per minute) and a field that no longer exists is left out with a line in the preview ("Start date not sent: the Jira field customfield_10015 no longer exists on this site. Choose another one in the field configuration."). Unmapped start date, Theme and priority still say so; a switched-off slot with a value says "… not sent: switched off in the field configuration."
- **GitHub Sync:** `buildTrackingIssue` takes the switched-off slots; the preview note lists them; a change alters the issue hash, so the next Sync offers to send it. The board already reports a field the board no longer has.
- **Webhooks and the daily check (the read side)** have nothing to re-point: Build Status comes from the issue state (GitHub) or status category (Jira), the counts from the children, and the board's status, iteration and date fields from the board mapping that already exists. They do not read the new table.

## 6. Decisions to confirm
1. Tracker-driven fields are shown but **not re-pointable** (e.g. Jira status category to Build Status stays fixed). Re-pointing would need new Product Velocity fields (e.g. Story points), and the dictionary does not grow.
2. GitHub board fields are edited in the existing Project boards card (listed, not duplicated, in the new table).
3. The GitHub managed-block sections Summary, Description and Hypothesis and the Jira summary and description cannot be switched off: the two-way compare depends on them.
4. Project scope only (no workspace default layer).
5. Switching a `pv:` label off removes it from issues at the next confirmed Sync.
