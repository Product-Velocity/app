**A project with initiatives linked to Jira issues can be unlinked; a confirmation asks whether to keep or delete the initiatives (issue #522).** This replaces the rule in `2026-11-02-jira-pull-in.md` that refused the unlink (PV008) while initiatives were linked, which Ashu hit on the RR test project (#519).

- **Where.** On Settings, Integrations, Jira, Projects: set the delivery tracker to "Not linked" and press **Unlink…** (only when the project has Jira-linked initiatives; otherwise Save works as before). The confirmation names the exact count and the consequences, with **Keep them in Product Velocity (recommended)** pre-selected and **Delete them (moves to the Trash)**. Anything but an explicit "delete" keeps the initiatives.
- **Database (`jira_unlink_project_release(project, delete)`, migration `20261118213153_jira_unlink_release.sql`).** A human workspace admin only (never Claude, a service account, a creator or another workspace), one transaction: the Jira link, issue tree and epic requests of every initiative of the project are removed; **Build Status is cleared** (status, status_changed_at, issues_total, issues_closed, delivery_progress_pct become empty: they are tracker-driven and nothing feeds them any more; Start Building and Build Completed dates are left as they are); with delete, the live initiatives go to the **Trash** with the existing `delete_items()` (restorable for 30 days, ranks close up; an initiative already in the Trash stays there); the read issue list, the project link and the project's tracker are removed. Jira itself is **never written**: its issues keep the `pm:` labels and the description sections. The clearing is audited as the person (source UI). The old `jira_unlink_project(uuid)` is left as it is.
- **The marker label re-adopts.** `jira_pull_in` is replaced (same signature): before creating an initiative from a Jira issue it looks for an initiative of the **same project**, live, with **no Jira or GitHub link**, whose marker label the issue carries (`<prefix>/<16 hex digits>`, the prefix whatever stealth mode chose; the hash is of the initiative id, as `markerFor` writes it). If found, the issue is linked to it (link mode `push`: Product Velocity wrote that issue; Build Status from the issue's category again) instead of creating a duplicate. It happens when a person presses **Pull in**, not silently while reading; an initiative of another project or in the Trash is never adopted. A marker is only on issues Product Velocity created or sent to, so initiatives that were pulled in from Jira (never sent) are not found this way and come back as new initiatives.
- **Parity: exception.** GitHub's project tracker change is a separate flow with its own checks; a GitHub twin is not built here.
- **Not verified.** Only tested against a local Postgres and the dev harness (Playwright); nothing was tried on a real Jira site.
