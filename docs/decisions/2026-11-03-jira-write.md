**Sync with Jira sends to Jira after a preview and a confirmation (issues #67 and #71).** The plan is `2026-11-03-jira-write-plan.md`; this records what was built and the details decided on the way.

- **Same flow as GitHub.** `start` reads the linked issues (read half), then compares the texts Product Velocity owns three ways against the hashes of the last sync (`item_jira_links.sync_base`, hashes only) and lists Received, Conflicts and To send. `confirm` writes ONE initiative at a time (the dialog shows "Writing x/y", a result and Try again per initiative), reads the issue again first and, if Jira's text is not what the preview showed, writes nothing and returns the new difference (`stale`); the ones before stay written.
- **What goes out** (`OUTBOUND_JIRA_FIELDS`: name, description, MoSCoW, G2M Date, Planned Start): the name as the summary (no code prefix: the issue key already identifies it, and an adopted issue keeps its own title style), the description as ADF, labels `product-velocity` and `pv:moscow/*` (people's labels stay; stale `pv:` labels are removed), the due date, and the start date and priority only when the site's field ids are mapped (the field mapping, #70, is not built: they are skipped with a note in the preview). The parent link is not sent: Product Velocity initiatives have no parent today.
- **Creating.** An initiative of a Jira-linked project without an issue gets one of the project link's initiative type, plus an opaque marker label (`pv:item/` and a hash, never the item id). A create whose answer was lost is found again by that label and linked, never created twice. Epics and tasks are never created by Product Velocity.
- **Description.** `markdownToAdf` (paragraphs, headings, bold, italic, code, safe links, lists, code blocks; anything else is text, `javascript:` links become text). Compared as plain text on both sides so formatting does not make false conflicts. It is written only when the Product Velocity text changed since the last sync (or Keep Product Velocity was chosen); if Jira's description holds a table, macro or mention, the preview says that sending replaces it.
- **Conflicts.** Only Jira changed: conflict, default Keep Product Velocity. Both changed: conflict, no default, Apply and send waits. No base yet (a pulled-in issue): a difference is a conflict, never a silent overwrite. Keep Jira takes the text into the initiative (`jira_apply_pull`, only name and description, audited as the person, one undo step).
- **Never.** No status, no transition, no sprint (the payload builder has no input for them); Initiative Status is never set from or to Jira (rule 6). No commercial field: `outbound-allowlist.test.ts` fills every dictionary field with a unique value and fails if any non-allowlisted one appears in a create or an update payload. Only creators and admins reach the engine; the database functions refuse viewers, service accounts and other workspaces; Claude (MCP) has no tool that sends to Jira, and platform staff are refused by the server action (rules 3 and 10).
- **Rate limits and sign-in.** A 429 or 503 is retried up to four times with back-off that honours Retry-After; a refusal is shown per initiative and not retried; ReconnectNeeded and a 401 say "sign in again" and stop.
- **Not verified here.** Jira cannot be reached from the build environment; everything is tested against a fake Jira. What only a real run on a Jira site shows: that a real description survives a round trip, the marker-label search (`/search/jql`), a real 429, and how the issue type of the project link behaves on create (required fields of the site's create screen may refuse a create; the refusal is shown per initiative).
