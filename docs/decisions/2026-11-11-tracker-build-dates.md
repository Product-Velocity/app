**Start Building and Build Completed come from the tracker's own dates, read from history, not from the day Product Velocity noticed (issue #421, Jira first).** Found on R8P-7049: Build Status was In progress (from the Jira status category) but Start Building was empty, because only a phase change set it and a followed initiative has no phase; and Jira initiatives had no Build Completed or build days (only GitHub had `gh_closed_at`).

- **Start Building (Jira)** = the earliest time the linked issue or any of its children and sub-tasks (the tree) first moved into the **in-progress or done status category** (issue history, `expand=changelog`; status names mean nothing, as for Build Status). The category of a status comes from Jira's `/status` list. The tracker's real date wins over the day we noticed (a later `start_building` is replaced); nothing is written when equal. A read with no history changes nothing. Initiative Phase and Initiative Status are never touched (rule 6), and no phase is invented for a followed initiative. Works for followed and owned initiatives alike.
- **Jira's own "Start date" and "Execution Start Date" are not a source** (Ashu, 2026-11-11): people edit them by hand, so they are opinions, not facts. They could be shown beside the computed date later; they are never used in it.
- **Build Completed (Jira)** = the linked issue's resolution date while its status category is done (`item_jira_links.jira_resolved_at`; cleared when it is reopened). `item_build_cycle()` (replaced, same columns) now reads: build started = the first time the phase became Build, else Start Building; build completed = the GitHub ticket close, else the Jira resolution. Build days are never negative: Start Building is a date, so a build is counted from the start of that day.
- **Backfill (Ashu, 2026-11-11).** No one-off job: the date read runs after the status and tree read in the same places (Sync with Jira, the daily check), for every linked initiative that is not frozen, so initiatives already in progress get their date the next time Jira is read.
- **Where it is stored.** `jira_apply_build_dates` (migration `jira_build_dates`), service role only, source "system", compare before write, audited with old and new value. Writes only through an existing Jira link of the connection and site it is called with; a deleted initiative is skipped. Nothing is written to Jira.
- **Failure is visible.** A failure of the date read never fails the status or tree read (ReconnectNeeded still propagates); it is logged (`sync-dates`, `check-dates`) and shown as a note on the initiative's card in the Sync dialog.
- **Parity exception (issue #422).** GitHub already has Build Completed. It has no honest "work started" signal in the issue state (an open issue never maps to In progress), so GitHub's Start Building waits for a decision on the signal (first linked pull request, or the first move of the board Status). `item_build_cycle()` already falls back to Start Building for GitHub too, so only the reading is missing.
- **Shown.** The Jira tab says "Build started …" or "Build completed … (started …, n days)" next to the issue's status, like the GitHub tab.
- **Not verified here.** Jira cannot be reached from the build environment; everything is tested against a fake Jira. What only a run on the Refinery89 workspace shows: that `expand=changelog` on `/search/jql` returns the status history for these issues, that `/status` lists the status ids used in it, and the resolution date for a done epic. Histories with more than 100 entries may be cut by Jira; the earliest moves are the ones that matter, and a cut history can only make the start later, never earlier.
