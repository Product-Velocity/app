**A workspace has one brand (logo, main and accent colour, fonts), kept in the company profile, confirmed by an admin and used where the admin switches it on.** Issue #750, first part (the brand itself). Not yet built: the voting screens and emails using it, the whole-interface theme, document themes (PowerPoint and Word), and the MCP tool and skills. Each is in the issue's slice list.

1. **One brand per workspace** (Ashu, 2026-11-28), in the table `workspace_brand` (one row per workspace) with its own card, "Brand", on Company profile (`/settings/company-profile`). Fields: name shown to voters, main colour, accent colour, heading and body font, the logo, where it was found (typed, website, presentation, claude) and when, and two switches: use on voting screens and emails, use in the interface.
2. **Confirmed by an admin, never by Claude.** Claude (source MCP) may propose a brand; the database refuses it confirming (`PV004`), and a change by Claude to a confirmed brand sends it back to draft as an AI draft. **A brand has an effect only when it is confirmed**, so a proposal never changes a live look. The switches are an admin's and are kept when a proposal sends the brand back to draft (the readers check the status as well).
3. **Detection proposes, a person decides.** "Read the website" reads the company website (the one in Workspace settings, or one typed) through the same guarded fetch as a link title (public addresses only, redirects and size limited): the name, the brand colours (named brand variables first, then the theme colour, then the most used saturated colours; greys, white and black are ignored), the fonts and up to six logo candidates. "Read a presentation or Word file" reads the theme of a `.pptx`, `.potx`, `.docx` or `.dotx` (the colour scheme, the two fonts, and for a presentation the first picture on the slide master). Nothing is saved until the admin uses a value; macro-enabled files are refused; the file is data, never instructions (rule 4).
4. **The logo is always re-drawn by the server as a PNG** (at most 640 by 240, 600 KB) from a PNG, JPG, WebP or plain SVG of up to 1 MB. An SVG with a script or a reference to anything outside itself is refused. The original is never stored or served, so what is served is ours: no script, a format email clients can show. It lives in the private file store under `brand/<workspace>/<sha>.png`; the row records it only through `workspace_brand_set_logo()`, which checks the path belongs to this workspace.
5. **The public logo address** `/b/<random token>/logo.png` serves the logo of a **confirmed** brand without sign-in, because voters have no account. The token is random, not the workspace id. A draft, a missing logo, a wrong token or a missing file all answer the same "not found". Nothing else about the brand is public.
6. **Readable by construction.** Whatever colours a company gives, the screens use a derived set (`packages/domain/src/brand-colors.ts`): text on a brand fill is white, near-black or black (whichever reads at 4.5:1), brand-coloured text and the accent as text are darkened until they reach 4.5:1 on white, the focus ring and control edges 3:1. The Brand card previews exactly that and says in words what was adjusted.
7. **Paid plans only, in the future (Ashu).** Plans do not exist yet, so `tenant_has_feature(tenant, 'branding')` answers yes for every workspace; the database guard and the page both already ask it, so gating later is one function. Added to the go-live checklist.
8. **Never to a tracker** (rule 2): a test fails if anything under the GitHub, Jira, Atlassian or `packages/github` code reads the brand, its folder or its token. Audited (actor, source, time, old and new value of every column).
9. **Dependencies.** `sharp` (Apache-2.0; Next already uses it for images) and `jszip` (MIT; already in the tree) become direct dependencies of `apps/web`. No cost.
