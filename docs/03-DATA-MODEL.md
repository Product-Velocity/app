# Data model (logical)

This replaces the earlier Excel field dictionary (`Roadmap_v3_field_dictionary_proposal.xlsx`), which predates teams, planning cycles, gates, outcomes, reports and breakdown routes. Types are logical; derive SQL. Every table has `id`, `tenant_id`, `created_at`, `updated_at`, `created_by`, `created_via` (UI / API / Claude MCP / GitHub / import / system) and RLS.

## Item fields: the field dictionary is the specification
**`docs/reference/item-fields.csv` (same content as `Roadmap_v4_field_dictionary.xlsx`) is the authoritative list of item fields: 165 fields.** This document only describes entities and relations. The field lists below are a summary and are superseded by the CSV wherever they differ.

Each field has a `key`, `type`, `allowed_values`, `origin`, `storage` and `ships_in_phase`:
- *Column on items / System-set column*: a real typed column on `items` (selects use a constrained text column or enum; allowed values come from `allowed_values`).
- *Related table*: relations, links, tags, files and threads get their own table.
- *Computed*: a view or function, never stored; it must still be available as a grid column.
- *GitHub-synced*: stored, read-only in the app, written by the sync engine.
- `ships_in_phase` says when the field gets its real data. **Every field with `ships_in_phase` 1 must exist in the schema by the end of Phase 1**, and every field of every phase must exist as a grid column (a field registry drives the Columns picker; fields from later phases show as "arrives in phase N" until then).

Rules:
1. Do not invent keys. Use the CSV `key` as the column name. If a field is wrong or missing, change the CSV (and the workbook) in the same PR and log it in `docs/DECISIONS.md`.
2. A test must compare the field registry in code with the CSV and fail on any difference (keys, types, storage, phase).
3. Editing mode (editable / computed / system / locked by GitHub) is in the "Grid columns and views" sheet of the workbook; the grid must follow it.
4. **"Scope" means three different things; keep them apart.** (a) *Portfolio scope* is the saved selection of projects a view shows. It is a view setting, never an item field. (b) *Target Markets* (`target_scope`) and *Live Markets* (`live_scope`) are go-to-market tag fields (where we plan to launch, where it is live). The keys keep the old name; the labels must not say "Scope". Not synced to GitHub; customer-safe (the sheet flag, confirmed by Ashu), so customer-safe views may show them. (c) *Planned Scope (#)* and *Scope Added (#)* are computed, read-only counts of sub-issues (epics and tasks) under the initiative's tracking issue.

## Tenancy and people
Platform staff (Product Velocity) are **not** tenant members: see `docs/15-ACCOUNTS-AND-ADMIN.md` (capability-based staff levels, separate non-tenant schema, access log, impersonation rules, `content_access_mode`).

- `tenants`, `tenant_members(user_id, role[viewer|commenter|creator|admin|leadership], is_approver, is_service_account)`. Implemented in `packages/db/migrations/0001`. Tenants are created only through `create_tenant(name)` (caller becomes admin). Members, tenant name and audit visibility are admin-managed; viewers see the tenant and its members. `invitations(tenant_id, email, role, is_approver, token_hash, expires_at, accepted_at/by, revoked_at)` (migration 0003): admin-only, one pending invite per email, token stored only as a SHA-256 hash, valid 7 days, single use; `accept_invitation(token)` requires the caller's *confirmed* email to match the invited email and refuses existing members. `invitation_preview(token)` (0006) lets an invite link show the workspace name, invited email and role before sign-in, and `invitation_account_exists(token)` (0007) says whether that email already has an account (so the page opens in sign-in or create-account mode); both answer only for the exact token of a pending, unexpired invitation and are callable by anonymous visitors. `tenant_directory(tenant)` (0004) lists a tenant's members with emails for members of that tenant. A tenant can never lose its last (active) admin (0005, extended in 0049; applies to everyone including the service role). **0049 (issue #216):** `tenant_members.status` (`requested|active|paused|revoked`; only `active` grants access, see `docs/15` 3.3), `tenants.allowed_email_domains`, `country`, `currency`, `time_zone`; the view `active_tenant_members`; `request_access_by_domain()`, `my_access_requests()`, `members_grid(tenant)`, `set_member_status(ids, status)`, `create_tenant(name, country, currency, time_zone, domains)` and `tenant_admin_emails(tenant)` (service role only). A service account can never be an approver (check constraint) and a write declared as `Claude MCP` cannot grant Approver (trigger).
- `projects(name, default_repo, github_installation_id, who_breaks_down[product|engineering|either])`; `project_members`. **Implemented (migration 0008):** `projects(name, default_repo, who_breaks_down)`; admins write, every tenant member reads; names unique per tenant. `project_members` and `github_installation_id` come later: until then all tenant members see all projects.
- `teams(name, project_ids[], github_team, focus_factor, split_maintenance, split_bugs, split_new, week_hours)`; `team_members(team_id, user_id|person_id, hours_per_week, skill_split jsonb)`; `time_off`. Unassigned engineers = `people` with no `team_members` row. **Implemented (0008), basic:** `teams(name, focus_factor, split_maintenance, split_bugs, split_new, week_hours, github_team)` with the time split adding up to 100; admins write; `item_teams(item_id, team_id)` links contributing teams (creators and admins write). Members, skills and time off come in Phase 5.
- `saved_scopes(name, project_ids[])`, `saved_views`. **Implemented (0008):** `saved_scopes(name)` + `saved_scope_projects(scope_id, project_id)` (a join table instead of an array, so a scope can never reference another tenant's project); creators and admins write. A scope only filters; it never owns a rank. **Implemented (0011):** `saved_views(name, columns[] in order, filters jsonb, group_by)`: shared by the workspace, creators and admins write, names unique per workspace ignoring case, at most 200 columns and 20 filters, audited. **Implemented (0015):** `weekly_updates(week_start, scope_key, scope_label, body, reviewed_at, reviewed_by)`: one per workspace, ISO week (a Monday) and scope; everyone in the workspace reads, creators and admins write, no delete; editing the text clears the review; the database sets who and when for a review and refuses it from Claude (PV004); audited. `weekly_item_changes(tenant, since)` returns rank, status and health changes from the audit log to every member. **Implemented (0014):** `item_activity(item, limit)`, a function (not a table) that returns the audit rows of one item and its related rows (found through the `item_id` of their create or delete row) to anyone who can read the item; refuses other workspaces. **Implemented (0013):** `item_groups(name)`, the workspace's list of Initiative Groups (`items.theme` keeps the name as text). Editors add a group by typing it (trigger `items_ensure_group`, case-insensitive match keeps the existing spelling; names unique per workspace ignoring case, 1 to 120 characters); only admins rename, merge or retire, through `rename_item_group`, `merge_item_groups` (returns the moved item ids), `restore_merged_group` (undo) and `retire_item_group` (refuses a group that still has items); `item_group_usage` counts items per group. Existing themes were backfilled. **Implemented (0012):** `saved_views.base_view` (one row per default-view name per workspace replaces that built-in view until it is deleted, which restores it) and `saved_views.customer_safe` (the columns must all be in `public.customer_safe_field_keys()`, the sheet's customer-safe flag; a customised default is never customer-safe). **Implemented (0041, R-97):** `saved_views.owner_id` (null = a workspace view that everyone reads and only admins write; else a private view only its owner reads and writes, any member including view-only roles), `visibility` (`workspace` | `private`, a check ties it to `owner_id`), `sort jsonb` (`{field, dir}`, one sort). Names are unique per owner (workspace views share one namespace); a private view is never customer-safe and never a customised built-in. Caps in the database with readable messages: 25 private views per person; 25 workspace views counting the 11 built-ins, i.e. 14 added ones (customised built-ins replace a built-in and do not count). New table `view_layouts(user_id null = workspace default, view_id | builtin, in_bar, position, hidden)`: the Roadmap view bar; each person reads and writes only their own rows, only admins write the workspace default (`hidden` marks a built-in hidden for everyone); written whole through `replace_view_layout` (at most six in the bar); audited. **0042** deletes every saved view once (reset; never re-run on real data). "In bar" is the word for the bar; "pinned" stays for pinned columns. A view never stores a project selection (that is the scope). Filter and column keys are checked by the app against the field registry, not by the database.

## Item (initiative) — fields
Identity: `key` (R-03), `title`, `summary` (customer-safe), `value_proposition` (customer-safe), `target_segments`, `home_project_id`, `contributing_team_ids`, `group` (theme), `screenshots[]`.
Priority: `stack_rank` (global, per cycle), `previous_rank`, `moscow`, `horizon`, `focus_area`, `value`, `confidence`, `size` (XS..XL), `effort_by_skill` jsonb, `decision` (set by humans only).
Timing: `start`, `end`, `date_precision` (day/month/quarter — customer-safe reports use quarter), `cycle_id`.
Health: `health` (On Track/At Risk/Delayed…, text-labelled), `status` = **Build Status** (**tracker-driven**, read-only: a closed ticket means the build is complete), `initiative_status` = **Initiative Status** (set by people only; same values), `delivery_progress` (derived), `planned_scope`, `scope_added`.
Spec: `spec_status`, `agent_ready` (bool), `ready_for_build_by`, `ready_for_build_at`; documents in `item_documents`.
Breakdown: `breakdown_route` (traditional|in_between|full_claude), `breakdown_status` (not_started|draft_proposed|awaiting_engineering|complete).
Planning cycle: `planning_status`, `deferred_count`, `deferral_reason`, `added_after_commit`, `candidate_tag` (carry_over|likely_carry_over|deferred|new|backlog).
Gates [R2]: `current_gate`, `gate_status`, `next_gate_due`.
Outcomes [R2]: `outcome_status`, `adoption_pct`, `review_date`, `realised_value`.
Automated: `created_at`, `created_by`, `created_via`, `updated_at`, `status_changed_at`, `github_issue_url`, `last_synced_at`.
Never synced to GitHub: value, confidence, customer fields, decision, rationale, outcomes, key results.

- `audit_log(tenant_id, entity, entity_id, field, old, new, actor_id, via, at)` — append-only (update, delete and truncate are rejected even for the service role); one row per changed field, written by triggers; readable by tenant admins only. `via` is taken from the transaction setting `app.via` (UI / API / Claude MCP / GitHub webhook / import / system), which only server code sets; if unset it is `API` for signed-in users and `system` otherwise.

## Items as implemented (migrations 0008 and 0009)
Column-by-column comparison with the dictionary: `docs/12-FIELD-GAP-LIST.md`. The summary below replaces the field names used above where they differ.
- **Columns follow the dictionary keys** (`item_code`, `initiative_name`, `value_12m`, `effort`, ...), with three exceptions that the registry maps: `owner_user_id` is the field `product_manager`, `end_date` is `g2m_date_est`, `home_project_id` is `home_project`. Labels in the app come from the dictionary, not from column names. Every field with `ships_in_phase` 1 exists. Selects are text columns with a check constraint holding the dictionary's allowed values exactly as spelled (`Must`, `On Track`, `Won't`, ...); `confidence` is High / Medium / Low. `theme` has no fixed list. `home_project` is stored as `home_project_id`. The effort-by-skill structure is `effort_by_skill` (jsonb).
- **Related tables:** `item_tags` (tag, target_scope, live_scope, segment), `item_links` (artifacts), `projects.github_board` (linked GitHub Project and field mapping, docs/04) and `item_github_links.project_item_id` (the board item of the issue) are columns added in 0037. `item_github_links.sync_base` (sha256 hashes of the name and three texts both sides agreed on at the last Sync with GitHub, never the text) and `sync_checked_at` are added in 0044 (0045 lets the base also hold hashes of the four board values: priority, group, due, size). `item_files` (screenshots and documents: name, type, size and an optional share token; the bytes are in the private Storage bucket `item-files`, see docs/04), `item_relations` (depends_on, related_to), `item_teams` (contributing teams). All with RLS, audit and no cross-tenant references. Creators and admins write, everyone in the tenant reads.
- **Computed fields:** view `items_computed` (one row per item, security invoker). Values that need data from later phases are null.
- **Keys:** `R-01`, `R-02`, ... counted per tenant, assigned on insert, never reused, not editable; numbers above 99 are not padded.
- **Stack rank:** one global list per tenant and planning cycle (`cycle_id` null until Phase 5), ranks 1..N. New items go to the end. Ranks are **not editable directly**; `move_item(item, position)` re-ranks in one transaction (checked at commit by a deferrable unique constraint), clamps the position, sets `previous_rank` on the moved item and writes one audit row per item whose rank changed. Deleting items closes the gaps in one statement. Saved scopes filter the list and never own a rank.
- **Description (0033):** `items.description`, Markdown, at most 20,000 characters, an ordinary editable text column (audited like every other; writable by Claude, which never sets rank, decision or value). It is the only long text allowlisted for the tracker body besides Summary and Hypothesis.
- **Soft delete (0017, #52):** `items.deleted_at` / `deleted_by`. RLS hides deleted rows from every reader, nobody can DELETE rows directly (grant removed), and `delete_items`, `restore_items`, `purge_items`, `discard_new_items`, `trashed_items`, `purge_old_trash` are the only ways in and out (security definer, answer per item, refuse Claude and service accounts with PV004). Rank uniqueness now applies to live items only (an exclusion constraint, error 23P01 instead of 23505); a deleted item keeps its old rank as the place to return to. `audit_row` writes only item code and name when an item is purged.
- **Who can write:** creators and admins write items; viewers, commenters and leadership read. Delete is allowed for editors (undo restores from the audit log). Column grants allow exactly the fields the dictionary marks Editable and shipped in phase 1.
- **System-set columns** are filled by a trigger and cannot be written by signed-in users: `last_edited_at/by` (a re-rank does not count as an edit of the items that shift), `phase_changed_at`, and the first date each phase was entered (`start_discovery` ... `start_rollout`), plus `previous_rank`, `ai_draft`, `created_at/by/via`.
- **Tracker-driven columns** (`status` = Build Status, `delivery_progress_pct`, `planned_scope`, `scope_added`, `github_issue_url`, `last_synced_at`, `status_changed_at`) cannot be written by signed-in users, on insert or update (column grants); only the service role (sync engine) writes them, and the audit log records the source.
- **Claude and service accounts** (source `Claude MCP`, or a member flagged `is_service_account`) cannot set Value (`value_12m`) or Decision, or change a rank (error `PV004`); they can create draft items and edit other fields.
- **`created_via`** keeps the write-provenance values (`UI`, `API`, `Claude MCP`, `GitHub webhook`, `import`, `system`) that every table and the audit log use; the dictionary's "Manual · Import · AI intake · GitHub" is not stored separately (open question in `docs/DECISIONS.md`).
- **References cannot cross tenants:** composite foreign keys `(tenant_id, id)` on project, people fields, team, scope and item links.
- **Performance:** policies use the hoisted pattern `tenant_id = any(array(select my_tenant_ids()))` (spike S7).

## Integrity rules
- `stack_rank` unique per (cycle, scope); changing it re-numbers in one transaction and writes audit rows.
- `status`, `delivery_progress` writable only by the sync engine.
- `decision`, `value`, `stack_rank` not writable by Claude/service identities (enforce in policy, not just UI).
- `gate_reviews` rows are append-only; rationale immutable.
- Audience-profile filtering is applied server-side when building report data, never in the template.
