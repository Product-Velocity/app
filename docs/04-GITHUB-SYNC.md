# GitHub sync specification

## Principles
GitHub App ("Product Velocity" bot); all writes are made by the app with an "on behalf of <user>" line in the body; Claude never writes to GitHub directly. Enterprise GitHub (Cloud) first; GitLab later behind the same interface (`packages/github` exposes a `SourceControl` interface).
Idempotent, retry-safe, webhook-driven with periodic reconciliation. Commercial fields **never** leave the app.

## Hierarchy mapping
Initiative → **tracking issue** in the project's default repo. Epics and tasks → **sub-issues** (epic issue with task sub-issues). Dates and simple metadata go through **issue fields** (Start date, Target date), which are available on Free, Team and Enterprise organisations (spike S3). **A Projects v2 link is part of R1 (reinstated 2026-10-22, R-010), as an optional per-connection setting:** one organisation-owned Project per connection; tracking issues and their sub-issues are added as items; the project date fields "Start date" / "Target date" are written from Planned Start / G2M Date (est) so the product roadmap shows in GitHub's Roadmap layout; Project Status, Iteration and Target date are read back (read-only). GitHub Apps can only reach **organisation-owned** projects (spike S2): user-owned projects are not supported and the setting says so. Everything works without a project; issue fields remain the fallback for dates. S2b confirmed hands-on 2026-10-23 (`docs/08`): the App reads private organisation projects, adds items, creates the two DATE fields itself and writes and reads back values; reads right after a write can lag. Hierarchy limits (spike S4b): 8 levels (parent plus 7 layers), tested; 100 sub-issues per parent documented; we use 3. Epic is not an issue type on Free organisations: use a label unless an admin creates the type.

## Field mapping
| App | GitHub | Direction |
|---|---|---|
| title, summary (technical part), acceptance criteria | issue title/body (templated block between markers) | app → GH; edits in the marker block are overwritten, outside are preserved |
| status (Build Status) | issue state / project status | GH → app (read-only in app). **A closed ticket means the build is complete, not the initiative** |
| initiative_status (Initiative Status) | (none) | not synced: set by people only (Active, On hold, Cancelled) |
| assignees | assignees | both |
| delivery progress | closed ÷ total sub-issues | GH → app |
| PRs, CI, releases | linked PRs, checks, release tags | GH → app |
| start/end dates | issue fields "Start date" and "Target date" (organisation fields) | both, optional; only these allowlisted fields are ever written |
| value, confidence, customers, decisions, rationale, outcomes, key results | — | **never synced** |

Add an automated test that serialises every outbound payload and fails if a non-allowlisted field name or value appears.

## Install and approval flow
Built in #31 (`/settings/integrations/github`, code in `packages/github` and `apps/web/src/lib/github`).
1. An admin (a person, never a service account or Claude) types the GitHub organisation name. The app stores a `github_connections` row in state **requested** and sends the admin to `https://github.com/apps/<slug>/installations/new` with a signed, one-hour `state` (workspace, admin, connection).
2. GitHub returns the browser to the App's **Setup URL**, `/api/github/setup`. The route checks the state, that the signed-in user is that admin, and (for an install) asks GitHub that the installation exists and belongs to the organisation that was entered. It records the installation id and sets **installing**. A non-owner gets `setup_action=request` with no installation id: state **waiting approval**.
3. Only GitHub's `installation` webhook (`created`, or `unsuspend` / `new_permissions_accepted`) at `/api/github/webhook` sets **connected**, then the repositories are read and Epic availability recorded. The app never claims to be connected before that. `installation deleted` disconnects; `suspend` suspends; `installation_repositories` re-reads the repositories (GitHub is the source of truth, a delivery is never trusted for the list).
4. The webhook finds its connection by installation id, or, if the install-return step never happened, by the one open connection waiting for that organisation. Two workspaces waiting for the same organisation are not guessed: the install-return step binds those. One installation belongs to one workspace (unique index).
5. **Disconnect** (`github_disconnect`) ends or cancels the connection, marks repositories removed and clears project default repositories. It does not uninstall the App on GitHub: that is the organisation owner's choice. Starting again creates a new connection.
Repositories that leave the installation are marked removed and clear any project default that pointed at them (linked items are flagged once items sync, #33 onwards). A project's default repository can only be set to an active repository of the workspace's connection (database trigger).
Tokens: installation tokens are created per installation, kept in server memory until a minute before they expire, never logged and never sent to a browser. The App private key and webhook secret are environment variables only; the webhook secret also signs the install state.
Not built in #31: user mapping (app users to GitHub logins, with #35 assignees), linking a Projects v2 board (#42), delivery storage with idempotency keys (#32; handlers are idempotent upserts until then).

### Setting up the GitHub App (one-time, by the App owner on GitHub)
- Webhook: Active, URL `https://<app domain>/api/github/webhook`, secret equal to `GITHUB_APP_WEBHOOK_SECRET`.
- **Setup URL**: `https://<app domain>/api/github/setup`, and tick "Redirect on update".
- Permissions and events: see the spike results below (Issues read/write, Metadata read; later slices add Pull requests, Checks, Issue types, organisation Projects). An organisation owner must accept every permission change on the installation page.
- The sandbox App used for the spikes is `product-velocity-sandbox` on `Product-Velocity` (Free plan). Create a separate App for real customers (docs/14).

## Pushing an initiative (built in #33, release 0.10.0)
- **Where:** "Sync with GitHub" (0.37.0; it first checks GitHub and applies what GitHub owns, see `docs/21`; the rest of this section describes the send half) in the bulk bar (up to 25 selected items) and in the item panel. It is enabled for creators and admins when the workspace is connected. Nothing is written before the person has seen the preview and pressed "Send".
- **What is written:** one tracking issue per initiative in the project's default repository (a linked item keeps its original repository). Title `R-12: Name`. The body is one **managed block** between `<!-- pv:begin item=<id> -->` and `<!-- pv:end -->`: Summary, **Description** (Markdown, 0.24.0), Hypothesis, Artifacts (links) and a link back. Labels `product-velocity`, `pv:project/<project>`, `pv:moscow/…` and `pv:rank/…` are created when missing; a push adds the ones the item should have and removes `pv:` labels that no longer apply, and never touches labels people added (see "Orchestration additions"). Text outside the block is never touched; edits inside it are overwritten on the next push that changes something.
- **The allowlist:** the only item fields read for a GitHub payload are `item_code`, `initiative_name`, `summary`, `description`, `hypothesis` (plus `moscow` and `stack_rank`, which only ever leave as the `pv:` labels above, never as text; plus the item's artifact links and the share links of files shared on purpose, private repositories only). Value, confidence, customers, decisions, rationale, key results, outcomes and markets are never read. `apps/web/src/lib/github/outbound-allowlist.test.ts` fills all 165 dictionary fields with sentinels, pushes through a fake GitHub, and fails if any non-allowlisted sentinel appears or any non-allowlisted field is read. User text is sanitised (our markers and @mentions are neutralised, links must be plain https).
- **Idempotent:** the link row (`item_github_links`, one per item) stores the issue and a hash of what was last sent: an unchanged item sends nothing. A create whose answer was lost is found again by the marker in the body instead of being created twice. If the linked issue was deleted or moved, nothing is recreated: the item shows an error and a person decides.
- **On behalf of:** the person who confirmed is recorded as the actor in the audit log (source UI) through `github_record_push()`, which only the server can call. The GitHub issue itself says it is managed by Product Velocity and does not name the person (the repository may be public and users have no GitHub login mapping until #35).
- **Failures:** a GitHub error shows a short message (never the response body or a token), is stored on the link and leaves the item unchanged; one item failing does not stop the others.
- **Follow-only links (0.10.2):** `item_github_links.mode` is `push` (the app owns the issue: the behaviour above) or `follow` (the item points at an existing issue and only reads from it). Pushing to a follow link is refused by the plan ("It follows issue #N read-only") and by `github_record_push` (error `PV006`). Used to link the Product Velocity roadmap to the real build issues without ever writing to them; status and progress flow in from GitHub once #32 and #35 exist.
- **Read-only repositories (0.10.3):** `github_repositories.access` is `read_write` (private repositories by default) or `read_only` (public ones by default). A read-only repository cannot be set as a project default (database guard), pushes to it are blocked in the plan and refused by `github_record_push` (`PV007`), and an admin switches access in Settings > GitHub (`github_set_repo_access`, which also clears project defaults that used the repository).
- **Not yet:** dates (issue fields need a permission the sandbox App lacks, and Projects v2 is #42), assignees (#35), optional pushes (#41), epics and tasks (#34), and detecting that someone edited inside the block (comes with inbound sync, #32).

## Inbound sync (built in #32 and the first part of #35, release 0.11.0)
- **Deliveries:** `/api/github/webhook` verifies the signature and handles `issues` deliveries for linked items. A delivery that touches no linked item is acknowledged and **not stored** (the build repo alone produces plenty). Otherwise it is stored once in `sync_events` keyed by `X-GitHub-Delivery` (only the issue number, repository, state, state reason and timestamps: never titles, bodies, comments or emails) and applied by `github_apply_issue()` in one transaction. A replayed delivery is a duplicate and changes nothing; information older than what is recorded is ignored.
- **Two statuses (decided 2026-10-23, R-029):** a closed ticket means the **build** is complete. That sets **Build Status** (`items.status`, read-only in the app) and **Build Completed** (`item_github_links.gh_closed_at`, the time the ticket closed). **Initiative Status** (`items.initiative_status`) is set by people only and no tracker ever changes it, because delivery, adoption and measurement come after the build. **Build time** (`item_build_cycle`) runs from the first time the Initiative Phase became Build (the audit log) to Build Completed; it is empty until both exist, and for a ticket closed as not planned.
- **State to Build Status:** closed as completed gives Done; closed as not planned gives Cancelled; reopened (from Done or Cancelled) gives Not started; the first look at an open issue gives an item with no status Not started (the fixed vocabulary Not started / In progress / Done / Cancelled, issue #247, migration 20261028225223; Jira will map its status categories To Do / In Progress / Done into the same four); an open issue never overwrites a human-set status. `status_changed_at` is set; Health and Initiative Phase are never changed from GitHub. The link records `gh_state`, `gh_last_activity`, `gh_synced_at`; follow links become `synced`.
- **Audit and flow:** every change is audited with the source "GitHub webhook" and no person. `item_stage_durations(tenant)` turns the audit log into one row per item, Status or Initiative Phase and stretch of time (entered, left, days), which is what flow and speed reports read ("how long was this in Discover").
- **Failures and repair:** a failed application is kept in the sync log with a short message and an attempt count (admins see it in Settings > GitHub and press "Run again"). "Check GitHub now" and the daily Vercel Cron (`/api/cron/github`, secret `CRON_SECRET`) retry failed events (up to 5 attempts), compare GitHub with every linked item and repair drift; changes found that way are logged with the source "reconcile". An issue that cannot be found is flagged on its link.
- **Epics, tasks and delivery progress (built in #34, release 0.13.0):** the tracking issue's sub-issues are epics (level 1) and their sub-issues tasks (level 2), read through the REST `sub_issues` endpoint and cached in `item_issue_tree` (title, state, assignee logins, who created it: app, Claude or engineer; read-only, derived, rebuilt each time). The tree is read again after every push, on `sub_issues` deliveries, on `issues` deliveries for an issue already in the tree (a task closing), and in the reconcile (button and daily cron). **Counting rule (one place, `summariseTree`):** work is counted at the leaves, so a task counts and an epic counts only while it has no tasks; work closed as not planned leaves the total. `issues_total`, `issues_closed` and `delivery_progress_pct` (closed ÷ total) are written to the item by `github_apply_tree` (service role only), with `gh_state` and `gh_last_activity` copied from the link; all are read-only in the app and audited with the source "GitHub webhook". A parent with 90 or more sub-issues shows a warning (GitHub's limit is 100).
- **Breakdown (Traditional route, #34):** the first tree refresh of an item whose tracking issue the app pushed sets Breakdown Route "Traditional" and Breakdown Status "Awaiting engineering". "Mark breakdown complete" (item panel, GitHub tab; creators and admins) calls `item_complete_breakdown`, which sets Complete and **freezes Planned Scope** to the number of tasks counted then; later growth is **Scope Added** (current total minus planned scope, never negative). Delivery progress is shown as provisional until the breakdown is Complete. Completing by a `breakdown-complete` label is not built yet (needs the parent's labels, see DECISIONS). The "In between" and "Full Claude" routes follow with the MCP server.
- **Blocked, stale, iteration, target date, schedule variance (0.41.0, #35):** `blocked_issues` and `stale_issues` are counted over the open epics and tasks by `countBlockedStale` (`@pv/domain`; blocked = label "blocked", stale = no activity for 14 days) and stored by `github_apply_tree_counts()` after every tree read; `gh_iteration` and `gh_target_date` are read from the linked board by the same pass as Delivery Status (the board's Iteration field, found by name, and the board's Due date field); `schedule_variance_pp` is worked out in the app from Delivery Progress, Planned Start and G2M Date (est), never stored. The "blocked-by" relation and a per-project stale window are not built.
- **Pull requests, CI, releases and repositories (0.42.0, #35):** `refreshExtras` reads, for one linked initiative, the pull requests that GitHub links to its issues (`closedByPullRequestsReferences` of the tracking issue and of every epic and task, one request per 40 issues), the rollup of the checks on the default branch of the primary repository (`statusCheckRollup`: SUCCESS is Passing, FAILURE or ERROR Failing, none is None, PENDING leaves the last value), and the releases of each repository (published, not draft; at most 10 repositories) and stores the counts, CI word, latest release since Build Started and the repository list through `github_apply_extras()` (audited as GitHub; nothing is stored when any read fails). It runs after every tree read, so it follows the same triggers (send, Sync with GitHub, `sub_issues` and issue deliveries, daily check), and checks and releases are read once per repository for a whole pass. `pull_request` (opened, closed, reopened, edited, ready for review, converted to draft), `check_suite` (completed, on the default branch) and `release` (published, unpublished, deleted, edited) deliveries refresh the initiatives they touch (a pull request through the issues it closes; at most 25 initiatives per delivery). **App settings needed:** permissions Pull requests, Checks, Commit statuses and Contents (all read) and the events Pull request, Check suite and Release; without them the values are filled by the checks only.
- **Assignees (0.43.0, #35):** `tenant_members.github_username` (own entry on the Account page, or an admin in Members; unique per workspace, case ignored) matches a member with an issue assignee. `items.assignee_ids` holds the people assigned in Product Velocity (written by `set_item_assignees()` for creators and admins, members of the workspace only), `item_github_links.gh_assignees` what GitHub shows now (stored by `github_apply_assignees()` after every issue read: send, Sync with GitHub, `issues` deliveries including assigned and unassigned, daily check). Sync with GitHub compares the two sets of **matched** people three ways (hash under the key `assignees` in `sync_base`) with the same rules as the texts; a login nobody uses is neither compared, changed nor taken over, a person without a username is never written. Keep GitHub stores the matched people through `github_pull_assignees()` (audited with the person, keeps the people without a username); Keep Product Velocity, or a change made only in Product Velocity, replaces the issue's assignees (the unmatched logins stay) after the confirm, **in private repositories only**, and the logins GitHub really set are read back (GitHub silently skips non-collaborators). Not built: assignees of the epics and tasks, a one-step Ctrl+Z for assignees taken over from GitHub.
- **Not yet:** assignee mapping to people (done: see above) (logins are shown as GitHub reports them; needs the user mapping), PRs, CI and releases, conflict highlight (#36), delivery storage for `pull_request`, `check_*`, `release`, queueing with `Retry-After` and ETag, and pruning of old `sync_events` (go-live checklist). Live updates need the App to be subscribed to the `issues` and `sub_issues` events; without them the daily check and "Check GitHub now" still bring the tree up to date. Since 0.28.0 the connection check has a **Live updates from GitHub** line that says which of the two are missing and where to switch them on (App settings > Permissions & events, then accept the change on the installation page).

## Incoming issues: choosing what comes in (built in #76, release 0.15.0)
- **Light record:** every issue of the connected repositories that is not part of an initiative's own tree is kept in `tracker_issues` (repository, number, title, type, labels, state, link, parent). Bodies, comments and people are never read. It is refreshed by the daily and manual check and by `issues` deliveries (these are not stored as sync events). Issues that are already an initiative's epic or task are left out.
- **Three states:** Not pulled (default for anything new), Ignored (with a reason), Pulled in. Not pulled and ignored issues are not initiatives: they are in no grid, rank, cycle or report, and nothing is ever written to them. Moves between Not pulled and Ignored are reversible; a pulled-in issue changes only if its initiative no longer exists.
- **Pull in** creates an Initiative (in a chosen project, named after the issue, source "GitHub issue #N") with a read-only follow link; Build Status comes from the issue's state at once. Choosing Epic or Task level and a parent waits for the Jira field mapping (#70). Up to 200 per call; one undo step discards the new initiatives again.
- **Rules for new arrivals** (admins): issue type, label or repository is X, then Ignore. A rule decides only the first time an issue appears; it never changes known issues or pulled-in initiatives. Rules are switched off, not deleted.
- **Audit:** every change of state, reason and initiative link is audited with actor and source.

## GitHub Project boards (built in part, 0.31.0, R-037)
- **One board per PV project.** `projects.github_board` (jsonb, admins only, migration 0037) holds the organisation Project (node id, number, title, url) and the field mapping. Only organisation-owned Projects can be linked (the App cannot reach personal ones). The App needs Organization permission **Projects: read and write**; the connection check says whether it has it. Linking, changing and unlinking are in Settings > GitHub > GitHub Project boards; the chosen board is checked against GitHub again on save.
- **What PV writes on the board item** (and only these; empty values write nothing and nothing is ever cleared): **Priority** from MoSCoW (Must P0, Should P1, Could P2; the map is stored per board), **Initiative** from Initiative Group (single select or text), **Due date** from the G2M Date (est), **Size** from the T-shirt effort estimate (XS to XL). MoSCoW, theme, G2M date and effort are the only item values read for the board (`BOARD_ONLY_FIELDS` and `planBoardItem`); the allowlist tests cover them.
- **Won't stays in PV.** A MoSCoW value that is not in the priority map (Won't) is pushed as an issue if the person sends it, but is not added to the board.
- **Existing fields are reused, never rewritten.** The mapping starts from the board's own fields by name (Priority, Initiative or Initiative Group, Due date or Target date, Size, Status). A single-select option the board does not have (for example no P0) is not created: the preview says "add it in GitHub" and nothing is written for that field. PV does not create fields or options and does not change a board's options (updating options of a single-select could clear values; to be tested in a spike before PV ever does it).
- **Status is GitHub's.** The board's Status (delivery status) is mapped only so it can be read back; it is never written, and it is not PV's own Initiative Status. Reading it back is the next slice.
- **In the push:** after the issue is written, the issue is added to the board (adding twice returns the same item) and the values are set; the board item id is kept in `item_github_links.project_item_id`. What would be written is part of the change hash, so changing a priority is a push. If the board step fails the issue stays written but is not recorded as synced, so the next push does the board again; if the board cannot be read, the preview says so and the board is left alone. The preview lists the board and its values per initiative.
- **Last Synced and Synced With (0.33.0, fields N46 and N47, derived, not stored):** *Last Synced* is the latest of `item_github_links.last_pushed_at` (last confirmed send), `item_github_links.gh_synced_at` (last time GitHub's state was applied) and `items.last_synced_at` (set when the issue tree was applied); *Synced With* is `GitHub · owner/repo`, plus `board "Title"` when the initiative is on the linked board (`project_item_id` is set), plus "follows #N, read-only", "last send failed" or "not sent yet" as it applies. Rules in `packages/domain/src/sync-info.ts`. Neither is ever sent to GitHub.
- **Delivery Status (0.34.0, field N33 `gh_project_status`, migration 0040):** the board's Status (the single-select field named in the board link's mapping), in the board's own words, stored in `items.gh_project_status` and shown read-only. No mapping to PV statuses: Build Status (`items.status`, the issue's state) and Initiative Status (people) are separate fields. It is filled by `syncBoardStatuses`: (1) in real time from `projects_v2_item` deliveries (a change of the Status field, or an item added or restored; GitHub does not send the new value, so the board is read again), (2) at every "Check GitHub now" and the daily check, (3) right after a confirmed send. A pass reads up to 1,000 items of the board, matches them to initiatives by repository and issue number, and `github_apply_board_status()` writes only initiatives whose status changed (audited with the source "GitHub webhook"); it also records `item_github_links.project_item_id`, so an initiative that was already on the board (pulled in) shows which board it is on. An initiative that is not on the board keeps its old value. If the board link has no Status field chosen (a link saved before 0.34.0), the board's field named Status is used; a board that cannot be used is named in the summary of the check ("Check GitHub now" and the daily check) instead of being skipped silently. The App must be subscribed to Project item events (and have Organization Projects permission); the connection check says whether it is.
- **Issue fields are not board fields (0.33.3):** GitHub's organisation *issue fields* (Priority, Effort, Start date, Target date) also appear as columns of a Project, but their values cannot be set with the board mutation (`updateProjectV2ItemFieldValue`); GitHub answers "Issue field values cannot be updated using the updateProjectV2ItemFieldValue mutation, they must be updated using the updateIssueFieldValue mutation". PV skips such a field (the other fields and the children are still written, the send succeeds), says which one was left out, and stores its id in `projects.github_board.mapping.unwritable` so the preview says so before a send. Writing issue fields themselves needs another call and a permission that spike S3b has not proven yet (#30). Until then dates from PV do not reach a board whose date column is an issue field; map a plain Date field of the board instead if you want them there.
- **Children on the board (0.32.0, migration 0038):** a confirmed send also puts the initiative's epics and tasks (all levels, read live from GitHub) on the board. They are only added; PV writes no field values on them. `item_issue_tree.board_id` and `board_item_id` record which board each child is on (a different board id means "not on the current board"), so only missing children are added; at most 40 per initiative and send, the rest at the next send. The preview counts them ("Also adds N child issues"), and an initiative whose issue did not change but whose cache holds children that are not on the board shows as changed. **Nothing is added in the background** (rule 3: GitHub writes need confirmation), so children created later wait for the next send; GitHub's own Project workflow for auto-adding sub-issues can do it hands-off if the team wants that (to be checked, not relied on). If the board step fails the issue is not recorded as synced, so the next send retries. A Won't initiative's children stay off the board.
- **Not built yet:** reading Status and moved dates back (`projects_v2_item`), reading an existing board's values into PV when importing (R-024), and a UI to edit the MoSCoW to Priority map.

## Pushed issues and Incoming (fix 0.33.1, migration 0039)
GitHub can announce a new issue before PV has saved its link (the webhook races the push). The issue was then recorded in Incoming as "Not pulled" and stayed there, and pulling it in failed on the existing link. Now `github_record_push` marks the recorded issue as pulled when it saves the link, `tracker_upsert_issues` repairs a record left as Not pulled or Ignored when the issue has a link, and `tracker_pull_in` answers "Already linked to R-98." instead of failing, without creating a second initiative.
**Not real time yet: a Project board's Status.** Webhooks arrive in real time for issue changes (opened, closed, edited, labels, sub-issues), but a change of a Project field such as Status (Backlog to Ready) is a different event (`projects_v2_item`) that the app does not handle yet and does not read. Reading delivery status and moved dates back from the board is the next slice of R-037.

## Breakdown routes
Field `breakdown_route` + `breakdown_status`.
1. **Traditional**: product pushes the initiative (tracking issue). Status "Awaiting engineering". Engineers create epics/tasks in GitHub. When engineering marks the breakdown Complete (label or app button), status = Complete. Sub-issues added before Complete count as planned scope; after Complete they are "Scope added". Delivery progress is provisional until Complete. Engineers' estimates and skills roll up into effort by skill.
2. **In between**: Claude drafts epics/tasks; engineering edits and accepts in the app; on accept the app creates the issues.
3. **Full Claude**: Claude proposes, an Approver signs off, the app creates the issues on confirmation.
Project setting "Who breaks down the work": Product team in app / Engineering in GitHub / Either (per item).
Each work item records `created_by` (app / claude / engineer).

## Events
Handle: `issues` (opened/edited/closed/reopened/assigned/labeled/transferred/deleted), `sub_issues`, `pull_request`, `check_suite/check_run`, `release`, `installation`, `installation_repositories`. (`projects_v2_item` is handled when a project is linked; confirm coverage in spike S2b.) Store each delivery in `sync_events` with `X-GitHub-Delivery` as the idempotency key; process via queue; verify signature; ack fast.

## Conflict handling
Last-writer-wins per field except marker-block content (app wins). If both sides changed the same synced field since `last_synced_at`, write a `sync_conflicts` row and highlight it in the grid; never silently drop. Deleted/transferred issues unlink and flag the item. Rate limits: honour `Retry-After`, use conditional requests (ETag), batch with GraphQL where useful.

## Spike results (see `08`)
- **S2** Projects v2 dropped from R1 (Apps reach organisation-owned projects only). **S3** issue fields work on Free organisations; dates map to them. **S4** 100 sub-issues per parent, 8 levels, REST endpoints exist; use REST for writes (`POST .../sub_issues` takes the numeric issue **id**), GraphQL for batched reads. **S5** proposed minimum App permissions: repository Issues (read/write), Pull requests (read), Checks (read), Metadata (read); organisation Issue fields (read/write); no Contents, Projects or Members. Events: `issues`, `sub_issues`, `pull_request`, `check_run`, `check_suite`, `release`, `installation`, `installation_repositories`.
- Still to confirm hands-on: writing issue-field values as an App (the issue-field permission is not yet identified) and the non-owner install request. **Least privilege for the real App:** the sandbox App also holds `actions`, `artifact_metadata`, `deployments`, `statuses` and `pull_requests`; the real one takes only what this document lists plus organisation Projects (read/write) and Issue types (read), and an owner must accept every later permission change.

## Orchestration additions (R-034, 2026-10-26)
- **Description (field N44, 0.24.0, migration 0033):** Markdown, up to 20,000 characters, written in the item panel (Write and Preview) or by an agent. It is the one long text that goes into its own `## Description` section of the managed block, between Summary and Hypothesis. It is sanitised like other user text (our markers and @mentions neutralised, cut at 20,000). PV stores Markdown only: raw HTML is not rendered in the preview, and anything HTML in the text is passed to GitHub as written, which sanitises it itself. Because the issue can be read by everyone with access to the repository, the field says so and the allowlist test stays the guard: value, customers and decisions are never read.
- **Issue number next to the Initiative ID (0.24.0):** derived from the link, not stored a second time (`item_github_links.issue_number` and `html_url` are the data). - **Labels PV owns (built, 0.27.0):** labels in the `pv:` namespace belong to PV. A push adds the `pv:` labels the item should have and **removes** the `pv:` labels it should no longer have (MoSCoW Must to Should: the old label goes, the new one is added; a renamed project swaps its `pv:project/…` label). Labels outside `pv:` are never touched, and the base label `product-velocity` is never removed. The labels are `pv:project/<project>`, `pv:moscow/<must|should|could|wont>` and a **rank band** `pv:rank/<top-10|top-25|top-50|later>`: the band, never the number. Value, confidence and the numeric Stack Rank are never sent. Only the app's writes to a **private** repository get these labels (public repositories are read-only for pushes by default). A band or MoSCoW change makes the item show as changed in the next push preview; the preview lists the labels and says that only `pv:` labels are managed. Change Type, Roadmap Category and Focus Area as labels are not built (decide per connection first).
- **Type, milestone and group (built, 0.29.0):** *Change Type* gives a `pv:type/new-feature` or `pv:type/improvement` label always, and the organisation's issue type when it has one with a matching name (New feature → `Feature`; Improvement → `Improvement` or `Enhancement`; matching ignores case; none found means label only, the push still succeeds). *Initiative Group* (`theme`) gives `pv:group/<slug>`. The **G2M Date (est)** gives a **milestone**: title `YYYY Qn` (calendar quarter), due date the quarter's last day (noon UTC); the milestone is looked up by title (open or closed) and created when missing; an item without a date leaves the issue's milestone alone. None of the three is written as text, and the allowlist test checks it. Quarters are calendar quarters (fiscal calendars later if asked). **Planned Quarter** (`g2m_quarter`, set by a person since R-114) is not written to GitHub; the milestone still comes from G2M Date (est), and the two can differ.

- **Files (built, 0.28.0, migration 0036):** the bytes live in the private Supabase Storage bucket `item-files` (created on first upload, reached only by the server with the service role); `item_files` holds name, `mime_type`, `size_bytes`, `share_token`, `share_updated_at` and is the only authority on who may see a file (RLS by workspace; creators and admins write). Allowed: PNG, JPEG, GIF, WebP, PDF, 10 MB each, 20 per initiative; the type comes from the first bytes (`sniffFileType`), never the name or the browser, so SVG/HTML/scripts are refused. A **share link** is `/f/<token>/<name>`: 256 random bits, unique, no login, one file only; off by default, turning it off removes the token (the address dies at once), turning it on makes a new token. The public route answers a wrong or revoked token with the same plain 404, names no workspace or initiative, and serves the file with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Referrer-Policy: no-referrer`, `noindex`, `no-store`. **GitHub:** a push adds a `## Files` section with the share links of the item's shared files, **only when the target repository is private** (`github_repositories.is_private`; unknown counts as public). For a public repository the preview shows a note and nothing is written. The files themselves are never uploaded to GitHub. Anyone who can read a private repository's issue can open the links, so the link is a decision per file. The share token is in the audit log like other column changes (visible to workspace members, who can already open the file). Links to Figma, Drive and similar still work as Artifacts. **Claude (0.44.0):** the MCP tools `add_file`, `set_file_sharing`, `list_files` and `remove_file` use the same rules and the same functions as the item panel; the sharing result tells Claude, and so the person, whether the link will reach the GitHub issue (private repository: on the next push; public or unknown: never).
