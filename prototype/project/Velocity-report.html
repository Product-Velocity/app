    For Ashu: how this is calculated, and what I need you to decide

    Definitions used in this prototype

    • Start is Start Discovery (the earlier of Start Discovery and Start Date, as Time to Market does). To Gate A / B / C ends on the date the gate was decided (gate_reviews), Total ends on Start Roll-Out. Build is Start Building to Start Test, the same as Actual Build (weeks).
    • Counted from: This stretch only restarts the clock at the previous gate (Gate B = Gate A decided to Gate B decided).
    • Time to decide is request to decision. A Hold keeps the request open, so the clock keeps running.
    • Only initiatives that reached the end of the measure are counted. Initiatives still running are never counted as zero; they are listed separately, and the in-flight table compares them with finished ones of the same size.
    • Size-adjusted compares a group with what its own mix of sizes would predict, so a team that mostly builds XL work is not called slow for it.
    • Percentiles: 10% of initiatives finish faster than P10, 80% within P80. Groups with fewer than 5 initiatives show the dots instead of a box.

    Questions

    • You listed total time and to roll-out. Gate C approval starts the roll-out, so both end on the same day and I merged them into Total. Do you want Total to run on to Completed (the 30, 60, 90 day tail)? It is one more option.
    • Objective, Key Result and Business Line are fields but not yet report filters or break-downs; the build adds them to the shared filter bar so every report gains them.
    • An initiative with several teams counts once per team (as the other reports do), so groups can add up to more than the total. An initiative has one Objective and one Business Line today; I assumed one Key Result as well. Is that right?
    • Decisions are shown for the team as a whole, never per approver (rule 8).
    • Not drawn here, to keep the page readable: scope added after commit, estimate against actual (already in Build time on Overview), blocked days. Say if you want any of them on this report.

    Insights: not in this version

    • Product Velocity is not connected to an AI, so it cannot write the "what stands out" findings itself. They are removed from the page. A person can ask their own Claude, through the MCP server, to read the report numbers and tell them what to look at.
    • To make that useful, the build adds notes and context for the connected Claude: which analysis to run on the velocity data and what to call out. First draft of that list, taken from what the earlier version computed:
      • Spread: slowest tenth against the median, and average against median (a long tail).
      • Sizes: do medians step up from XS to XL, or does a larger size finish faster than a smaller one?
      • Groups: a team, Key Result, Objective, Business line, Initiative Group or Focus Area that is clearly slower or faster than its own mix of sizes predicts (groups of 5 or more only).
      • Waiting: share of elapsed time spent waiting for gates or in queues, and the largest wait.
      • Trend: the latest two quarters against the ones before.
      • Decisions: the slowest gate to decide, and requests waiting well beyond the median.
      • In flight: initiatives already past what 80% of finished ones of the same size needed.
      Each call-out gives the numbers behind it and ends with a question for the team. Team level only, never a person. Claude reads and explains; it sets no values.
    • Question: should an admin be able to edit these instructions per workspace? The Help pages "AI co-workers" and "AI use-cases and documents" would be updated in the same PR, as the project rules require.
